# Безпека й приватність

[English](SECURITY.md) | Українська

APEXREST працює з виконуваним кодом застосунків і доступом до середовищ Oracle. Використовуйте явні цілі, перевірену довіру проєкту та з’єднання з мінімальними привілеями. Поточна бета має відкриті умови перевірки; див. [стан реалізації](docs/implementation-status.uk.md).

## Повідомлення про вразливість

Не додавайте облікових даних, cookies, wallets, рядків з’єднань із паролями, реальних даних клієнтів чи неочищених браузерних звітів у публічні issues. Перевірену публічну пошту безпеки не налаштовано. Зв’яжіться з власником репозиторію приватно через уже перевірений канал; не припускайте, що неперевірена адреса належить проєкту.

Власник має ввімкнути GitHub private vulnerability reporting, перш ніж його можна пропонувати як підтримуваний канал. Для звичайних нечутливих помилок використовуйте [GitHub issues](https://github.com/apexrest-dev/apexrest-codex/issues).

## Облікові дані та звіти

Облікові дані SQLcl залишаються в його сховищі іменованих з’єднань. Посилання APEXREST містять назви, а не паролі. CLI `--password-file` має бути звичайним файлом без символьного посилання, доступним лише власнику, а URL ORDS мають використовувати HTTPS, крім loopback. SQL-копії записуються з доступом лише для власника (`0600`). Браузерний стан автентифікації приватний у керованому home, має обмежені права файлів і строк дії. Інтерактивний вхід локальний; у цьому процесі вимкнено записування, traces, знімки екрана та відео.

Звіти типово обмежені й приватні. Публічні пакети випуску виключають кеші виконання, стан автентифікації та сирі докази з локальними шляхами машини. Очищення є додатковим захистом; воно не може виявити кожен бізнес-секрет. Переглядайте кожен артефакт перед поширенням, включно зі знімками, навмисно зробленими під час дозволеної UI-перевірки.

## Довіра до проєкту й хоста

SQL, тести та APEXlang проєкту є виконуваним кодом. Перегляньте проєкт перед наданням довіри. Метадані БД, коментарі, довідка й тестовий вивід не є вказівками розширювати дозволи. Приватна політика має залишатися поза репозиторієм.

Повноваження локального користувача й хоста залишаються визначальними. APEXREST не може завадити агенту з необмеженим доступом до оболонки/файлів змінити власну доступну для запису політику. Наявну обмежену вказівку користувача можна записати для імпорту розробки/тестування; вона не дозволяє сторонніх змін або production. Production-ключі підпису й конфігурація перевірки належать захищеному зовнішньому runner, недоступному недовіреному коду репозиторію. Довірені ключі схвалення й production-цілі перелічено у файлі `production-trust.json`, що належить адміністратору; APEXREST ніколи його не записує й відмовляється його використовувати, якщо поточний користувач володіє ним або може його змінити. Схвалення production у Windows не підтримується. Не запускайте привілейованих процесів на коді pull request.

## Ланцюг постачання

Завантаження постачальників контролюють дозволені хости, HTTPS, зафіксовані хеші, обмеження розміру й безпечне розпакування. Залежності npm використовують зафіксований lockfile; ревізії браузера — зафіксований Playwright. Playwright перевіряє завантаження браузерів із CDN; APEXREST не фіксує незалежно SHA-256 цих файлів. Це явне відкрите обмеження ланцюга постачання. Змінні дзеркал `PLAYWRIGHT_DOWNLOAD_HOST` із середовища ігноруються, тому середовище не може непомітно перенаправити це незафіксоване завантаження. Кеш завантажень із ключами SHA має належати поточному користувачу й не бути доступним для запису групі чи іншим. Керовані інструменти записують digest виконуваного файлу й дерева в `runtime.json` і замінюються, якщо вони більше не збігаються; інструменти, встановлені попередніми випусками, отримують цей запис під час першої перевірки, тобто довіра встановлюється під час першого використання.

Жоден npm postinstall hook не завантажує інструментів. Запуск MCP не завантажує залежностей. Прийняття ліцензії Oracle та встановлення системних пакетів Linux потребують окремої згоди. Перегляньте копію коду й локальний digest пакета перед встановленням; встановлення з репозиторію не гарантує підписаного стабільного випуску.

## Розгортання та відновлення

План прив’язує код, інструментарій, ідентичність і поточний стан цілі. Apply порівнює поточну ціль та історію міграцій із планом і заново обчислює ризик автентифікації/авторизації з поточного експорту. Міграції, скрипти пакетів і SQL-тести з клієнтськими командами SQLcl блокуються. Apply зберігає дозвіл, перевірки розбіжностей, зафіксований код, перевірену SQL-копію наявного застосунку та стійке володіння/історію. Локальна координація захищає runners зі спільним керованим home; вона не забезпечує послідовності незалежних машин.

Не знімайте оренди розгортання у фазі запису через завершення TTL. Oracle DDL міг зафіксуватися. Перед повторенням звірте ціль, журнал і копію з адміністратором. Відновлення метаданих APEX не відновлює бізнес-даних або руйнівних змін схеми. Див. [безпеку розгортання](docs/deployment-safety.uk.md).

# Участь у розробці

[English](CONTRIBUTING.md) | Українська

APEXREST розробляється в [apexrest-dev/apexrest-codex](https://github.com/apexrest-dev/apexrest-codex). Код, CLI-довідка й інструкції навичок агента — англійською. Публічні документація та діаграми підтримуються англійською й українською. Зосереджуйте зміни на задачі й узгоджуйте твердження з доказами.

Оновлюйте кожен англійський `.md` посібник та його `.uk.md` відповідник разом, включно з взаємними посиланнями мов. Перекладайте пояснення, приклади запитів і описи зображень; зберігайте виконувані приклади, конфігураційні ключі, шляхи, версії та межі доказів. Машиночитні докази, сторонні повідомлення й початкова специфікація зберігають оригінальний вміст. Навігація й пошук сайту залишаються в обраній мові, перемикач відкриває відповідну сторінку. Після змін документації виконайте `npm run docs:check` і перевірки сайту.

## Підготовка копії репозиторію

Використовуйте Node 24 LTS і зафіксований lockfile:

```sh
git clone https://github.com/apexrest-dev/apexrest-codex.git
cd apexrest-codex
npm ci --ignore-scripts
npm run build
```

Після змін коду, залежностей, навичок чи ресурсів виконайте `npm run plugin:sync`. Він збирає й оновлює самодостатній пакет плагіна в репозиторії, який використовується для встановлення з репозиторію. Комітьте отриманий пакет разом зі змінами джерел. `plugins/apexrest-apex/runtime/` і `plugins/apexrest-apex/resources/` — згенерований результат, позначений `linguist-generated` у `.gitattributes`; не редагуйте їх вручну. Змініть джерела й повторно виконайте `npm run plugin:sync`.

Звичайне збирання не розгортає застосунку й не встановлює бінарних файлів Oracle. Налаштування нативного хоста, завантаження постачальників, підключення й віддалена інтеграція мають власні передумови. Див. [початок роботи](docs/getting-started.uk.md).

## Перевірка зміни

```sh
npm run lint
npm run typecheck
npm run test:unit
npm run test:contracts
npm run test:installers
npm run site:build
npm run test:packaging
```

Виконуйте перевірки, відповідні зміненій поведінці, зокрема build перед пакувальними тестами. Після свіжої збірки виконайте `npm run plugin:check` для порівняння пакета в репозиторії зі згенерованими ресурсами/середовищем виконання. `npm run test:repository-plugin` перевіряє пакет у новому ізольованому профілі Codex без з’єднання чи запису в Oracle. Зміни нативної реєстрації також потребують реальної ізольованої перевірки життєвого циклу Codex; зміни адаптера Oracle чи застосунку — відповідних реальних доказів компілятора/цілі, коли ціль дозволена й доступна. За відсутності потрібного середовища запишіть блокер, а не підміняйте результат фікстурою. Див. [тестування](docs/testing.uk.md).

## Інженерні вимоги

- Зберігайте строгий TypeScript, використовуйте ESM та узгоджуйте публічні схеми CLI/MCP з поведінкою.
- Зберігайте метадані Oracle `.apex`, ID, сторонні компоненти та зміни робочого дерева.
- Прив’язуйте плани до коду й цілі; зберігайте перевірки копій, розбіжностей, дозволів, координації та невідомого результату.
- Не додавайте в контроль версій секретів, браузерного стану, локальних середовищ виконання, сирих бізнес-даних чи приватних копій.
- Оновлюйте документацію та відповідні записи приймання/доказів, коли змінюється поведінка чи перевірка.
- Переглядайте оновлення залежностей із зафіксованими URL/хешами, ліцензіями, архітектурним рішенням і фактичними доказами сумісності.

Зберігайте без змін `APEXREST_CODEX_PLUGIN_BUILD_SPEC.md` і україномовний `APEXREST_COMPOSER_IMPLEMENTATION_PLAN.md` як історичні джерела. Записуйте дозволені поправки вимог у правилах проєкту й архітектурних рішеннях; не переписуйте специфікацію для спрощення приймання.

## Створення pull request

Опишіть конкретну проблему й отриману поведінку. Додайте фактично виконану валідацію, її середовище та відкриті обмеження. Пояснюйте компроміси безпеки чи сумісності, коли вони суттєві. Відтворіть помилку перед розширенням виправлення й уникайте стороннього форматування чи змін залежностей.

Для роботи Codex використовуйте гілку `codex/`, якщо maintainer не просить іншу назву. Перед комітом перевірте staged diff на облікові дані й приватні артефакти. Внесок не дозволяє розгортань, платних ресурсів, тегів випуску чи публікації.

## Робота над випуском

Перед пакуванням виконайте `npm run plugin:sync`, потім `npm run plugin:check`, та перевірте нативне встановлення з репозиторію через `npm run test:repository-plugin`. `npm run release:dry-run` створює непідписані локальні бета-артефакти й звіт готовності. Стабільна готовність потребує актуальних доказів, прив’язаних до точного незмінного коду. Публікація потребує окремого захищеного процесу й дозволу maintainer; вона не входить до звичайного build чи pull request. Див. [налаштування публікації](docs/publishing.uk.md).

Повідомляйте про проблеми безпеки за [SECURITY.uk.md](SECURITY.uk.md), не через публічні вкладення із секретами.

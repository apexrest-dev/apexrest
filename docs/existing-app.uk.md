# Перенесення наявного застосунку

[English](existing-app.md) | Українська

Створіть каркас `existing-app` та налаштуйте точну наявну development/test-ціль й іменовані з’єднання. Для застосунку з одним редактором використайте опцію working copy під час перенесення або ініціалізуйте синхронізацію на наявному узгодженому дереві джерел:

```sh
apexrest project adopt --env dev --app-id ID --working-copy --json
apexrest apex sync --env dev --action status --json
# Alternatively, initialize the configured source directory directly:
apexrest apex sync --env dev --action init --json
apexrest deploy plan --env dev --out plans/dev.json --json
apexrest deploy apply --plan plans/dev.json --json
```

Початкова операція створює один APEXlang-експорт та одну SQL-копію. Вона встановлює відсутній каталог джерел або вимагає точного збігу наявного переліку файлів з експортом. Конфлікт зберігає локальні файли й приватні проміжні дані. Придатний активний запис повторно використовується без експорту, зокрема після нового процесу чи чату. Зберігайте `.apex`, Oracle ID, спільні LOV, автентифікацію та всі файли сторінок у системі контролю версій.

Редагуйте локальні джерела, потім виконуйте plan і apply. Планування надає результати компіляції, перевірки ідентичності, метаданих і змін. Повторний working-copy plan/apply не робить повних експортів, включно з fingerprint та backup; імпорти залишаються повними. Початкова SQL-копія відновлює лише baseline. Зафіксовані проміжні застосовані джерела доступні для перевірки без автоматичного відкату до кожного імпорту. Дивіться [запобіжники розгортання](deployment-safety.uk.md).

Користувач обирає одного редактора: під час циклу застосунок змінює лише цей плагін. Зміни через Builder або інші засоби потребують явного refresh. Метадані оновлення можуть виявити можливі зовнішні зміни; незмінні або null-значення не доводять незмінність кожного компонента. `status` читає лише локальний стан і змінені файли та не підтверджує актуального стану сервера. Дати експорту й імпорту інформаційні.

```sh
apexrest apex diff --env dev --json
apexrest apex diff --env dev --comparison live --json
apexrest apex sync --env dev --action refresh --json
apexrest apex sync --env dev --action invalidate --json
```

Автоматичний diff порівнює локальні хеші файлів з останнім успішним застосованим snapshot або початковим baseline до першого імпорту. Джерело порівняння явне; це не повне семантичне покриття компонентів. `--comparison live` явно робить експорт. Refresh відхиляє локальні незбережені зміни до будь-якого експорту. Для відомої чистої копії він зберігає попередні джерела/копії та встановлює новий серверний baseline. Злиття змін не виконується. Invalidate зберігає джерела, копії й журнали та не знімає блокування перерваних або невідомих записів.

Без опції working copy перенесення зберігає наявний експорт одного формату в новий каталог із `LOCAL_EDITS_CONFLICT` для наявних файлів. Ручний `apex export --env dev --output review/export-UUID` не активує та не просуває checkpoint. Без активної синхронізації deployment і diff зберігають повний експорт. Production, нові застосунки, DB-міграції та виконання пакетів використовують цей шлях; перед DB-операціями явно виконайте invalidate. Ціль, указана в адміністраторському `production-trust.json`, є production, навіть якщо `apexrest.json` стверджує інше, тому working-copy sync для неї заборонено.

Стан міститься у приватному ignored `.apexrest/sync/<targetDigest>/state.json` та прив’язаний до канонічного root, проєкту, environment, цілі, каталогу джерел і версії toolchain/runtime. Пошкоджені записи/артефакти та невирішені імпорти блокують повторне використання без прихованого експорту. Зберігайте активні baseline, SQL-копії, deployment snapshots та історію координації під час очищення. Явна звірка може робити експорт як виняткову діагностику та не дозволяє повторювати записи.

[Локальні регресійні докази](evidence/working-copy-local.json) рахують справжній код sync/plan/apply на імітованій межі Oracle. Connected baseline + три зміни з перезапуском, автентифікована браузерна перевірка та окреме відновлення початкового стану — NOT RUN: development-ціль не дозволена. Release-перевірки збереження компонентів/static files/MMD, імпорту без змін та непідтримуваних компонентів зберігають окремий обсяг; fixtures не є доказом live Oracle.

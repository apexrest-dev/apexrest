## Post-deploy re-authentication after full imports — local, 2026-10-06

Implemented: before E2E specs run, a read-only probe opens the base URL with the saved browser state. A visible password field without the configured marker makes E2E `blocked` with `reason: "reauth_required"`; otherwise the specs decide as before. When that is the only gap in the required gate, `deploy apply`/`ship --mode apply` stop the run in the new `awaiting_reauth` state with `POST_DEPLOY_REAUTH_REQUIRED` (exit 4, `blocked`) instead of `POST_DEPLOY_TEST_FAILED`; the run is not succeeded and a working-copy checkpoint is not advanced. After the user's interactive `apexrest test auth`, the new `apexrest deploy verify --run UUID` rechecks the post-import target identity, update metadata and local migration history, reruns all configured suites against the unchanged gate and records `succeeded`, `failed` or `awaiting_reauth`. It never imports. The agent never handles passwords.

[Local Oracle record](evidence/post-deploy-reauth-local.json) on the isolated APEX 26.2 application 92620: the probe found the real login page after the earlier full import, `ship --mode apply` stopped in `awaiting_reauth` with SQL 5/5 passed, and `deploy verify` without a new login passed the drift check and stayed `awaiting_reauth` without importing. Resuming to `succeeded` after an interactive login is NOT RUN; it needs the user's login.

Local checks: typecheck, lint, 368 unit tests (one existing skip; nine new for re-authentication), 61 contract tests, 27 packaging tests, plugin synchronization and documentation checks.

## Pattern catalog

Stable source IDs preserve other sources; a replacement requires a reviewed update. Registry `sourceReviews` bind every page decision to its exact source hash. The builder rejects missing or stale reviews, unknown source anchors and patterns absent from their page reviews.

## Fast-development follow-up backlog (2026-11-25, local, branch `feat/fast-development`)

Work items are APE-405 to APE-438 in Linear; each section names its backlog ID. Implementation, repository tests, compiler evidence, native import and browser observations are reported separately.

**A01 compound page edits ([APE-405](https://linear.app/apexrest/issue/APE-405)).** `packages/core/src/edit/transaction.ts` plans every operation of one request against one immutable page snapshot, combines the text edits, parses the result, has each operation read its change back and only then replaces the file atomically under the source-edit lock after rechecking the digest. `project action:edit` (`project.edit`) accepts `set` operations (the `patch` properties and `query`) and `insert` fragments in one request. `patch` and `insert` now run through the same transaction with unchanged results. Operations target only components of the snapshot read. Verified by `tests/unit/source-edit-transaction.test.ts` (combined write, byte-identical failures, stale digest, MCP routing) and the existing patch and insert tests. No compiler or native import run is claimed for this change.

**A02 context after every edit ([APE-413](https://linear.app/apexrest/issue/APE-413)).** `patch`, `insert` and `edit` results carry `context` computed from the exact bytes written (planned bytes for a dry run) by `packages/core/src/edit/context.ts`: the new digest, changed and inserted targets with their editable values, and removed targets. Unchanged components are omitted, and line moves alone do not count as a change. The delta lists at most 40 entries and cuts query text at 2000 characters, pointing to `action:context` when bounded; `context:"full"` and `context:"none"` are available. Verified by `tests/unit/source-edit-transaction.test.ts` (delta values, digest reuse, external-edit conflict, removed columns, modes).

**A03 working filters ([APE-422](https://linear.app/apexrest/issue/APE-422)).** The `addFilter` edit operation (`packages/core/src/edit/filter.ts`) inserts the item and an optional container region, makes every target report, cards region or chart series submit the item (a missing property, a scalar list or an Oracle-exported `[ ... ]` array) and adds one refresh of all targets, in one page transaction. Optional complete replacement SQL is applied per report (with its column contract), cards region or chart series. Predicates are never rewritten: a target query that does not bind the item is refused (`FILTER_NOT_BOUND`), as are other region families. Verified:
- Repository tests (`tests/unit/source-edit-filter.test.ts`): submitted items and binds of every target, array extension without reformatting, one refresh of all targets, unchanged existing dynamic actions, refusals and conflicts.
- Local preview (SQLite) in the same test file: the filtered report shows all rows initially, only matching rows for a changed value, no rows for a value without matches, and all rows again after clearing.
- Oracle offline compiler (SQLcl 26.3.0.260.1620, 26.2 profile) on a scratch `customer-crm` project: report filter on page 10, cards and chart-series filter on page 20, both `passed` with 0 diagnostics and 0 warnings (`docs/evidence/fast-dev/addfilter-compiler-2026-11-25.json`, local, not committed).

A free sequence gap is used when one exists; otherwise the listed columns are renumbered. Interactive reports keep the primary default saved report's `displayColumn` list in the same order. **A09 project entity contracts ([APE-406](https://linear.app/apexrest/issue/APE-406)).** `packages/core/src/entities.ts` defines a versioned, project-owned contract in `entities/<id>.json`: read source (complete SQL or a table/view), ordered key, typed and labelled fields with optional shared or static LOVs, explicit read authorization (a scheme or `public: true`), and an optional write contract with its own scheme, table, operations and lost-update rule. Contracts have a stable id (the file name), a schema version and a SHA-256 digest of their canonical parsed JSON, so key order and formatting do not change the digest. Checks beyond the schema report duplicate fields, keys that are undeclared, optional or dated, incomplete write contracts (no write scheme, a missing or non-number row-version column, required read-only fields an insert cannot set) and a write table that differs from the read table. `project action:entities` (`entity.list`) lists contracts with digests and diagnostics; the JSON schema is published as `entity-contract`. Scaffold specifications and Composer blueprints are unchanged. Verified by `tests/unit/entities.test.ts` (digest stability, explicit security, diagnostics, broken and mismatched files, MCP routing). Connected validation is A10; generation from contracts is A11.

**A10 entity contract validation ([APE-415](https://linear.app/apexrest/issue/APE-415)).** `packages/core/src/entity-check.ts` adds `project action:entity_check` (`entity.check`). Offline it repeats the structural checks, confirms referenced shared LOVs exist in the application sources and lists every assumption it cannot verify (tables, columns, authorization schemes, the read SQL's projection), with no database call. ## Measured Oracle optimizations, Slice G (2026-11-22, local)

All measurements are on the local APEX 26.2.0 / Oracle 23.26.4 target with SQLcl 26.3, application 26220. The evidence is in ignored `docs/evidence/fast-dev/export-direct-2026-11-22.json` and `preview-oracle-2026-11-22.json`. No optimization in this slice was adopted; each decision keeps the existing path.

**Scoped export, direct versus SQLcl ([APE-385](https://linear.app/apexrest/issue/APE-385), [APE-387](https://linear.app/apexrest/issue/APE-387)).** `node scripts/bench/export-direct.mjs` compares `apex export -exptype APEXLANG -skipExportDate -expOriginalIds` with the documented `APEX_EXPORT.GET_APPLICATION(p_type => 'APEXLANG', p_with_original_ids => true, p_with_date => false)` on the same scope. It is read-only, and the two modes alternate across 5 repetitions.

| Scope                       | Cold, own SQLcl process (SQLcl / direct) | Warm, one session (SQLcl / direct) | Content                                                                                          |
| --------------------------- | ---------------------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------ |
| Page 10                     | 3,151 / 3,133 ms                         | 1,421 / 1,402 ms                   | Same file; canonically equal                                                                     |
| Full application (27 files) | 3,486 / 3,507 ms                         | 1,943 / 1,757 ms                   | Same files; text canonically equal; binary static files need a separate encoding through a query |

- **Selection limits are identical.** Both interfaces accept only one component per APEXlang call: a list such as `PAGE:10,PAGE:1` fails with ORA-20987. A shared LOV is not an APEXlang export component in either interface (ORA-20987).
- **Export identity is unchanged by the switch.** Both interfaces export with original ids and without the export date.
- **Where the time goes.** About 1.7 s of a cold page export is SQLcl startup and connect; the server-side export is about 1.4 s.
- **Decision.** The direct export brings no material benefit (under 2% for a page) and would need its own file transport for binary content. The SQLcl adapter is kept, so the backup, readback and canonical-comparison paths are unchanged.

**Validation reuse ([APE-389](https://linear.app/apexrest/issue/APE-389)).** A repeated validation of an unchanged snapshot costs 77–104 ms warm (2.4–2.7 s cold) against a 9–14 s page ship. Planning validates the whole source and then the selected effective snapshot in one process, so the second run is already warm. Reuse would save under 1% of a ship. Decision: not implemented. The separate pre-import validation and Oracle's import validation are unchanged.

**Connected preview profile ([APE-379](https://linear.app/apexrest/issue/APE-379)).** `node scripts/benchmark-preview-oracle.mjs` wraps the preview's Oracle link and counts, per page request:

- round trips;
- batch segments;
- APEX session creations;
- time the main thread is blocked in `Atomics.wait`.

Starting the connection costs 2.3 s and 9 round trips. That includes the schema prefetch and one APEX session warm-up.

| Page            | Request, median of 10 | Main thread blocked | Round trips (segments) | Queries | APEX sessions |
| --------------- | --------------------- | ------------------- | ---------------------- | ------- | ------------- |
| 10 (report)     | 21.7 ms               | 19.0 ms             | 2 (3)                  | 1       | 0             |
| 20 (dashboard)  | 16.5 ms               | 14.7 ms             | 2 (3)                  | 1       | 0             |
| 30 (dashboard)  | 40.7 ms               | 38.0 ms             | 3 (5)                  | 2       | 0             |
| 1, 80 (no data) | under 1 ms            | 0                   | 0                      | 0       | 0             |

- **Round trips.** Each request with data makes one batched round trip for its queries and one for the closing rollback. A round trip takes about 9–15 ms.
- **Blocking.** About 90% of a request is main-thread blocking, and the worst event-loop delay equals the Oracle wait (17–35 ms).
- **Edit loop.** A title edit on page 10 appears in the connected page in 27.6 ms median, with 2 round trips.
- **Not exercised.** These pages run no PL/SQL with APEX context, so per-request APEX context initialization was not measured.

**Batching and context reuse ([APE-396](https://linear.app/apexrest/issue/APE-396)).** Queries are already batched. Merging the closing rollback into the last batch would save one round trip, about 10 ms per request. A browser reload dominates that, so it is not material for the edit loop. Request-scoped APEX context reuse has nothing to save on this workload, which had no per-request APEX sessions. Decision: deferred. It needs a page with APEX-context PL/SQL first.

**Main-thread blocking ([APE-395](https://linear.app/apexrest/issue/APE-395)).** A request blocks the event loop for at most about 40 ms on these pages, and the preview serves one developer. Decision: deferred, with this measurement as evidence. Moving a whole request to a worker is reconsidered if a page blocks for a noticeable time (hundreds of milliseconds).

# Розгортання та відновлення

[English](deployment-safety.md) | Українська

## Робоча копія з одним редактором

Для наявного development/test-застосунку явний `apex sync --env dev --action init` обирає [робочу копію](existing-app.uk.md). Початкова синхронізація перевіряє ідентичність, створює один APEXlang baseline та одну SQL-копію з перевіреною сумою під deployment-координацією й порівнює метадані до/після експорту. Звичайні status/оновлення панелі читають лише локальні файли. Ready зберігається між чатами/перезапусками; зміни каталогу джерел/root/цілі/toolchain потребують явного повторного встановлення стану. Baseline та останні застосовані джерела — приватні довговічні snapshots поза звичайним очищенням результатів.

Нові плани використовують schema v2: `mode: full-export|working-copy`, `backupStrategy: fresh-export|initial-backup`. Working-copy план прив’язує sync ID/revision, digest baseline/checkpoint та ID/checksum початкової копії. Він читає свіжу ідентичність, метадані оновлення й історію міграцій, компілює поточні джерела та включає додані/видалені security-файли в оцінку ризику. Apply зберігає авторизацію, строк плану, фіксацію джерел і свіжі перевірки під deployment ownership. Він перевіряє початкову SQL-копію без експорту, довговічно записує `importing` перед записами й просуває успішний checkpoint лише після перевірки ідентичності та проходження всіх наявних required suites. Два плани однієї ревізії не можуть застосуватися разом. v1 залишається допустимим на старому шляху; активний sync потребує нового прив’язаного v2 плану.

`LAST_UPDATED_ON`/`LAST_UPDATED_BY` читаються з явним серверним форматуванням; null залишається null, помилки запиту блокують роботу. [Oracle описує ці поля](https://docs.oracle.com/en/database/oracle/oracle-rest-data-services/25.3/orrst/op-apex-applications-application_id-get.html). Змінені значення блокують можливі зовнішні зміни. Незмінні/null метадані не є повним контролем drift компонентів: користувач явно приймає одного редактора. DB-операції несумісні з активним working-copy планом; явний invalidate повертає повний шлях. Production і нові застосунки зберігають цей шлях.

Підтверджений імпорт із невдалою перевіркою дає `verification_failed` зі старим успішним checkpoint. Втрачена відповідь, перерваний запис або помилка локального збереження після мутації блокуються як `outcome_unknown`; залишений `importing` теж потребує звірки. Invalidate не видаляє невідоме ownership. Явна звірка status може експортувати для діагностики та не дозволяє повторних записів. Відновлення baseline використовує окремий backup-bound план, свіжі запобіжники й точний дозвіл; старий sync стає invalidated перед початком запису відновлення. Відкат до кожного проміжного імпорту поза цією версією. Перервана локальна установка джерел теж залишає заблокований довговічний запис для перевірки замість позначення неповної копії як ready.

Описаний нижче повний експорт зберігається для проєктів без активного sync та окремих restore-планів. Поточні локальні [вимірювання](evidence/working-copy-local.json) доводять кількість експортів і файлову поведінку лише з fixture-методами Oracle; connected імпорти, браузерна перевірка й відновлення для цієї зміни — NOT RUN.

Поправка користувача від 2026-09-12 трактує явний запит створити/оновити/імпортувати визначений застосунок розробки/тестування як дозвіл на необхідний імпорт у цих межах. Після перевірки конкретного плану агент може записати наявну вказівку як короткостроковий локальний deploy grant для точного проєкту, цілі та плану; він має зберегти сторонню політику й запис дозволу та видалити grant після спроби. Не запитуйте той самий дозвіл двічі й не зупиняйтеся на плані. Кожен локальний deploy grant має містити `planDigest`, що дорівнює digest перевіреного плану, і `expiresAt` не пізніше за `expiresAt` плану; інакше apply блокується з `DEPLOY_APPROVAL_REQUIRED`. Це фіксує вже надану згоду, не вигадує її, не дозволяє сторонні записи в базу й не замінює захищені production-підписи. Ідентичність, SQL-копія, перевірки розбіжностей, координація, фіксація коду та обробка невідомого результату залишаються обов’язковими.

Для перевірки лише застосунку можна використати явно дозволений ізольований профіль із компілятором, реальним звірянням SQL лише для читання та спостереженнями вбудованого браузера, зберігши початковий профіль обов’язкових наборів і його історичні результати. Відсутність налаштованих автоматизованих наборів означає, що вони не запускалися, а не що SQL/E2E пройшли. Див. [навичку тестування](../plugins/apexrest-apex/skills/apexrest-test/SKILL.md#application-only-verification-scope).

Розгортання працює на чистій підтримуваній інсталяції APEX без службових таблиць APEXREST. Типовий режим — `deploymentControl: "local"` (також коли поле не задано). Він зберігає незмінну історію міграцій і володіння схемою в `$APEXREST_HOME/deployment-control/`; запити до службових таблиць чи DDL у цьому режимі не виконуються. Окремі посилання на з’єднання для читання та розгортання дають змогу мінімізувати привілеї.

`deploy plan --env dev --out plans/dev.json` читає точні унікальну назву бази, сервіс, схему, робочий простір та ідентичність застосунку, експортує цільовий вміст, хешує код/конфігурацію/інструментарій і виконує валідацію справжнім компілятором. Валідація успішна лише тоді, коли вивід компілятора містить маркер успіху й не містить ознак помилки, зокрема підсумків на кшталт `3 errors`; інакше — `VALIDATION_UNCONFIRMED`. План діє 30 хвилин, а apply відхиляє план із довшим строком дії як `PLAN_TAMPERED`. Планування експортує в локальний проміжний каталог, але не імпортує в БД. Повний імпорт включає сторінки й спільні компоненти; зміна однієї сторінки все одно є повним імпортом. Непідтримувані компоненти має блокувати справжній компілятор; покриття не є універсальним.

`deploy apply --plan plans/dev.json` повторно перевіряє план, зовнішню політику, поточну ціль і компілятор. Поточна ціль та історія міграцій мають збігатися з їхніми копіями в плані; розбіжність дає `PLAN_TAMPERED`. Ризик автентифікації й авторизації обчислюється заново з поточного експорту, а не береться з плану: змінені файли автентифікації/авторизації та зміни вмісту APEXlang, як-от `authentication`, `authorizationScheme` або блоки автентифікації/авторизації, дають `PLAN_TAMPERED`, якщо план їх не містить. Скопійований SQL-експорт із контрольною сумою створюється до будь-яких записів у застосунок чи схему щоразу, коли застосунок існує на цілі, незалежно від значення `backupRequired` у плані. Файли копії доступні лише власнику (`0600`), а проміжні каталоги експорту Oracle видаляються після використання. Після другої перевірки розбіжностей код фіксується й хешується. Впорядковані незмінні міграції стійко записують `started` перед виконанням (типово локальний файл, у database mode — рядок БД); змінені контрольні суми або невирішені результати блокують наступні плани. Скрипти пакетів виконуються після міграцій. Перша помилка SQLcl зупиняє виконання; транзакційність DDL не припускається.

Локальний режим виконує послідовно runners зі спільним керованим home для тієї самої БД/сервісу/parsing schema, включно з різними застосунками цієї схеми. Підтверджено завершеного власника на тому самому хості можна замінити лише у фазі підготовки. Після невідомого результату володіння записом зберігається й ніколи автоматично не знімається після збою. План прив’язує backend, обсяг та ідентичність локального сховища. Зберігайте deployment-control: нова машина чи видалена історія не можуть визначити з Oracle раніше застосовані міграції. Для кількох машин використовуйте один стійкий runner/home та зовнішнє послідовне виконання CI або явно виберіть database mode. Локальні файлові блокування не гарантують розподіленої координації БД. Файли блокувань і атомарні записи стану публікуються лише після збереження на диск їхнього вмісту та запису каталогу. Файл блокування без читабельного власника, старший за 30 секунд, дає `LOCK_CORRUPT`: переконайтеся, що жодна операція apexrest не виконується на жодному хості, потім видаліть указаний файл блокування й повторіть спробу. Автоматичної команди відновлення для цього випадку немає.

Необов’язковий `deploymentControl: "database"` зберігає наявний журнал БД і оренду рядка. Лише цей явно вибраний режим потребує перевірених таблиць `templates/database-control/install.sql`. Setup їх не створює. Heartbeat — 20 секунд, TTL — 90 секунд; можна повторно отримати лише прострочену оренду підготовки. Початкова реалізація БД між runners усе ще потребує реальної конкурентної перевірки Oracle. Непомітного переходу з database mode немає, оскільки він міг би відкинути історію міграцій.

Застосунок імпортується з явними workspace/schema/ID, ідентичність перевіряється, обов’язкові набори виконуються. Порожній/пропущений/заблокований обов’язковий набір провалює перевірку. Неочікувана помилка перевірки після підтвердженого імпорту дає `POST_DEPLOY_VERIFICATION_FAILED`, а не невідомий результат імпорту. Скасування, тайм-аут або втрата оренди після запису дають `outcome_unknown`; автоматичного повторного apply немає. `deploy status --run UUID` читає ціль/експорт/історію для звіряння й ніколи не перетворює невизначеність на успіх.

utPLSQL потрібен лише коли SQL-набір вибраний/обов’язковий. Проєкт лише застосунку може розгортатися без нього; не видаляйте справді обов’язкових наборів заради успішної перевірки. Підтримка чистого APEX змінює сховище контролю, а не вимоги до дозволів чи якості. Плани, створені до появи поля координації, потрібно згенерувати заново.

`deploy restore-plan --backup UUID --out plans/restore.json` перевіряє копію та поточну ціль, створює новий план і потребує grant для його точного digest. Apply створює нову копію, потім відновлює один повний нерозділений Oracle-експорт `f<ID>.sql` із явною ціллю встановлення. Розділені/невідомі формати блокуються. Якщо застосунку не було під час створення плану, перевірка ідентичності після відновлення використовує alias, записаний разом із копією, тому успішне відновлення не позначається як `outcome_unknown`. Це відновлює лише метадані APEX; бізнес-дані й руйнівні зміни схеми потребують окремого DBA-відновлення. Загальні руйнівні/привілейовані зміни та зміни автентифікації залишаються заблокованими до явного процесу відновлення.

## Міграції та клієнтські команди SQL

Міграції мають лежати безпосередньо в `database.migrationsDir` і мати впорядковані назви на кшталт `0001__customers.sql`. Планування відхиляє підкаталоги (`INVALID_MIGRATION_LAYOUT`), інші назви (`INVALID_MIGRATION_NAME`) і два файли з однією числовою версією (`DUPLICATE_MIGRATION_VERSION`). Нова міграція з версією, нижчою за найвищу застосовану, дає `MIGRATION_OUT_OF_ORDER`. Міграції виконуються в порядку числових версій, потім скрипти пакетів за шляхом.

Скрипти міграцій і пакетів можуть містити лише SQL та PL/SQL. Рядок, який SQLcl або SQL*Plus може сприйняти як клієнтську команду, наприклад `host`, `!`, `$`, `@`, `@@`, `start`, `spool`, `connect` або допустиме скорочення, додає ризик `sqlcl-script-control`. Як і інші ризики без перевіреного процесу відновлення, він блокує дозвіл із `RECOVERY_REVIEW_REQUIRED`. Сканер навмисно повідомляє з запасом, зокрема про рядки всередині коментарів і рядкових літералів. SQL-тести перевіряються так само (див. [тестування](testing.uk.md)). У режимі CLI сесії SQLcl для скриптів міграцій і пакетів, `apex import`, відновлення метаданих і SQL-тестів запускаються з рівнем обмеження `-R 2`, який блокує команди хоста й запис файлів, зокрема `spool`, але дозволяє `@file`.

## Схвалення production

Ціль є production, якщо її середовище в `apexrest.json` має `kind: "production"` або її `targetDigest` указано в `productionTargets` файлу `$APEXREST_HOME/production-trust.json`. Указана там ціль є production незалежно від конфігурації проєкту: локальні deploy grants, working-copy sync і віддалені тести для неї заборонені.

Production apply потребує `CI=true`, `APEXREST_APPROVAL_FILE` і `APEXREST_APPROVAL_PUBLIC_KEY_FILE` на захищеному POSIX runner, а також файлу довіри, що належить адміністратору:

```json
{
  "schemaVersion": 1,
  "approvalKeys": [{ "sha256": "SPKI_DER_SHA256_OF_APPROVAL_PUBLIC_KEY", "reviewer": "release-approver" }],
  "productionTargets": ["TARGET_DIGEST_FROM_REVIEWED_PLAN"]
}
```

APEXREST ніколи не записує цей файл. Він має бути звичайним файлом, а не символьним посиланням, належати іншому обліковому запису, наприклад root, не бути доступним для запису поточному процесу й не бути доступним для запису групі чи іншим (`PRODUCTION_TRUST_UNPROTECTED`). Відсутній файл дає `PRODUCTION_TRUST_REQUIRED`; нечитабельний або недійсний вміст — `PRODUCTION_TRUST_INVALID`. Запуск від імені власника файлу, зокрема root, якщо файл належить root, відхиляється. Windows відхиляється з `PRODUCTION_TRUST_UNSUPPORTED`, бо ACL не перевіряються. Змінна середовища лише вибирає публічний ключ: SHA-256 цього ключа у формі SPKI DER має бути в `approvalKeys` (`APPROVAL_KEY_UNTRUSTED`), а необов’язковий `reviewer` там має збігатися з атестацією.

Зовнішня атестація Ed25519 містить `planDigest`, `planId`, `projectId`, `targetDigest`, `expiresAt`, `reviewer` і `signature`. Підпис покриває канонічний JSON усіх інших полів. Кожне значення має відповідати плану й проєкту, а строк атестації не має минути; інакше apply завершується з `APPROVAL_INVALID`. Атестації без `planId` і `projectId` відхиляються строгою схемою, так само як `approved=true`. Репозиторій не може надавати чи змінювати ключ перевірки або файл довіри runner. Жодна операція, доступна агенту, не підписує схвалень. Якщо користувач runner може видалити `production-trust.json`, він також може прибрати класифікацію production з цього файлу; саме схвалення production без файлу все одно блокується.

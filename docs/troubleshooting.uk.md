# Усунення несправностей

[English](troubleshooting.md) | Українська

Почніть з `apexrest doctor --json`, потім використайте повідомлену можливість або код помилки. Знайдений виконуваний файл, перевірений компілятор, виявлення нативним Codex і робоче з’єднання БД — окремі стани.

## Команда apexrest не знайдена або меню застаріле

Дія **Install plugin** і керований setup створюють засіб запуску в керованому `bin`; саме встановлення інструментів і пряма команда `codex plugin add` його не створюють. Скористайтеся [налаштуванням PATH](getting-started.uk.md#використання-cli) або відкрийте готовий пакет у копії репозиторію:

```sh
node plugins/apexrest-apex/runtime/apexrest.mjs
```

Якщо локальна копія все ще показує категорії або **Preview only**, перебудуйте її через `npm run plugin:sync` і повторно відкрийте TUI. Переконайтеся, що запускаєте саме цю копію. Поточне меню має шість дій; Enter на **Review** виконує встановлення/видалення. Решта робочих дій доступна через явний CLI та плагін Codex.

Якщо файли керованого плагіна вже видалено, його засіб запуску більше не має коду для запуску. Використайте команду з копії репозиторію для встановлення плагіна знову. Перед видаленням **Keep plugin files** дозволяє зберегти засіб запуску придатним до роботи.

## Збережені з’єднання відсутні або не проходять перевірку

TUI читає локальне сховище SQLcl. `connection add` створює лише посилання APEXREST і не додає з’єднання до SQLcl. Збережіть з’єднання в SQLcl, потім натисніть Ctrl+R у списку. Через CLI використовуйте `connection list --saved`, щоб читати те саме сховище.

Перевірте `APEXREST_SQLCL`, `APEXREST_JAVA_HOME` і `APEXREST_HOME`, якщо інструменти встановлено в іншому місці. Виберіть точну збережену назву, зокрема регістр і пробіли. Відсутні чи прострочені облікові дані виправляються в SQLcl; успішний запуск TUI не підтверджує з’єднання з базою.

## Плагін встановлено, але інструментів немає

Після реєстрації чи оновлення почніть нову задачу Codex. Перевірте список нативних плагінів і ввімкнення в тому самому профілі Codex. Перевірений хост Codex 0.154.0 потребує пакета сумісності: portable manifest пройшов валідацію схеми й виявлення, але не надав MCP-інструментів на цьому хості.

Підтримуваний шлях реєстрації описано в [посібнику зі встановлення з репозиторію](getting-started.uk.md#встановлення-плагіна). Не додавайте другий глобальний MCP-сервер, щоб приховати невдале нативне встановлення. `needs-user-action` після setup може означати успішну реєстрацію за відсутності налаштованого з’єднання або згоди на ліцензію Oracle.

## SQLcl наявний, але компіляція не проходить

Перевірене локальне поєднання — SQLcl 26.1.2.132.1334 із Java 21. Системна Java може відрізнятися; керований setup або `APEXREST_JAVA_HOME` вибирає потрібну JRE. Читайте точну діагностику компілятора замість покладатися лише на код завершення: SQLcl може надрукувати помилку й завершитися з нулем. Тому валідація вимагає маркера успіху й відсутності ознак помилки; інакше вона повідомляє `VALIDATION_UNCONFIRMED` із виводом компілятора.

Зберігайте згенеровані Oracle `.apex/apexlang.json` та ID компонентів. Ніколи не вигадуйте версію MMD й не редагуйте внутрішніх таблиць APEX для обходу несумісності компілятора. Використовуйте довідку вибраної версії інструментарію та вносьте цільове виправлення коду.

## Перевірка цілі чи політики не проходить

| Симптом                                             | Дія                                                                                                               |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `PROJECT_TRUST_REQUIRED`                            | Перегляньте виконуваний код проєкту й додайте його канонічний шлях до приватної політики користувача.             |
| Відсутнє середовище чи невідповідність ідентичності | Перевірте вибраний `--env`, з’єднання, БД/сервіс, workspace, схему та ID застосунку.                              |
| Прострочений чи невідповідний план                  | Створіть новий план із потрібного поточного коду й цілі; не редагуйте план на місці.                              |
| Немає службових таблиць для звичайного розгортання  | Використовуйте типовий local mode; таблиці потрібні лише явно вибраній координації БД.                            |
| Обов’язковий набір порожній чи заблокований         | Надайте справжні тести/залежності або врегулюйте дозволений обсяг; не зараховуйте його як успішний.               |
| `DEPLOY_APPROVAL_REQUIRED`                          | Запишіть deploy grant із точним `planDigest` цього плану та строком дії не пізніше за план.                       |
| `PLAN_TAMPERED`                                     | План більше не відповідає поточній цілі, історії чи коду; створіть і перегляньте новий план.                      |
| `RECOVERY_REVIEW_REQUIRED`                          | Приберіть клієнтські команди SQLcl чи руйнівні зміни/зміни автентифікації або скористайтеся перевіреним процесом. |
| `PRODUCTION_TRUST_*` або `APPROVAL_*`               | Попросіть адміністратора runner перевірити `production-trust.json`, ключ схвалення й атестацію.                   |
| `PASSWORD_FILE_UNSAFE`                              | Використовуйте звичайний файл пароля без символьного посилання, доступний лише власнику (`chmod 600`).            |

Облікові дані з’єднання належать локальному сховищу SQLcl. Не додавайте їх у повідомлення про помилку чи запит. Див. [конфігурацію](configuration.uk.md).

## Браузерна автентифікація чи діаграми не працюють

Завершіть вхід локально й перевірте доступність справжньої сторінки застосунку. Автентифікація автоматизованого браузера та вбудований сеанс Codex — окремі контексти; успіх одного не доводить автентифікації іншого. Явно дозвольте потрібні SSO/CDN origins для автоматизованих тестів.

Дочекайтеся завантаження асинхронних регіонів діаграм APEX перед оцінюванням порожньої діаграми. Після дії фільтра перевірте передавання потрібних елементів сторінки та оновлення кожного відповідного регіону. Проєктуючи AJAX-оновлення, використовуйте нативні настанови дашборда в плагіні. Шар завантаження або стара вкладка з незавершеною навігацією можуть потребувати свіжого огляду сторінки перед змінами коду.

## Помилки offline, проксі чи завантажень

Заздалегідь завантажте точні артефакти постачальника з ключами SHA та потрібні кеші npm/браузера. `--offline` ніколи не переходить до мережі; відсутній кеш блокує залежність, пошкоджений артефакт не проходить перевірку цілісності. Окремо перевірте місце на диску, проксі/CA та платформні залежності браузера. Кожна спроба завантаження переривається після 60 секунд без нових даних і повторюється, загалом до трьох спроб. `PROXY_UNSUPPORTED` означає, що проксі налаштовано, але поточний Node не може його застосувати: запустіть із `NODE_USE_ENV_PROXY=1` на Node 24 або новішому чи заздалегідь заповніть офлайн-кеш. `UNSAFE_CACHE_DIRECTORY` означає, що кеш завантажень не належить поточному користувачу або доступний для запису групі чи іншим.

`--install-os-deps` явно запитує встановлення системних пакетів Playwright і може потребувати підвищених прав. Прийняття ліцензії Oracle залишається окремим від згоди на технічне налаштування. Під час запуску MCP залежності не завантажуються.

## Setup заблоковано чи перервано

Конкурентний setup повідомляє `LOCKED`. Підтверджено завершений процес того самого хоста можна відновити через спеціальну перевірку відновлення. Невідомий власник, інший хост чи перерване відновлення потребують огляду; не вгадуйте, що активне блокування застаріло.

`LOCK_CORRUPT` повідомляє про файл блокування без читабельного власника, старший за 30 секунд, зазвичай залишений перерваним процесом. Переконайтеся, що жодна операція apexrest не виконується на жодному хості, потім видаліть указаний у повідомленні файл блокування й повторіть спробу. Автоматичної команди відновлення для цього випадку немає.

Нативні пакети копіюються через проміжний каталог та атомарне перейменування. Повторний запуск перевіряє завершені компоненти. Зберігайте сторонні плагіни та приватний керований стан; видалення всього не є звичайним виправленням.

## Розгортання повідомляє `OUTCOME_UNKNOWN`

Не повторюйте apply і не знімайте оренду запису лише через завершення TTL. Oracle DDL або імпорт застосунку могли зафіксуватися до втрати з’єднання. Огляньте стан розгортання, журнал, поточну історію цілі й SQL-копію; звіртеся з адміністратором цілі перед вибором відновлення.

Для записаного запуску використовуйте `apexrest deploy status --project PROJECT --run RUN_ID`. Відновлення має власний план і точне схвалення та відновлює лише метадані APEX. Бізнес-дані й схема потребують власної процедури. Див. [розгортання та відновлення](deployment-safety.uk.md).

## Повідомлення про відтворювану проблему

Додайте версію плагіна, ОС/архітектуру, версію Codex, точну очищену команду, код помилки й найменший приклад коду, який її відтворює. Відрізняйте локальні фікстури від спостережень Oracle чи нативного хоста. Перевірте діагностику на шляхи, облікові дані й бізнес-дані перед прикріпленням до [issue](https://github.com/apexrest-dev/apexrest-codex/issues). Для чутливих знахідок використовуйте [приватне повідомлення](../SECURITY.uk.md).

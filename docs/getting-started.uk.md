# Початок роботи

[English](getting-started.md) | Українська

Встановіть CLI з npm, відкрийте його термінальне меню для встановлення інструментів і плагіна, потім налаштуйте пряме з’єднання SQLcl або ORDS HTTP(S). Пакет npm містить готове середовище виконання, тому копія Git-репозиторію, збирання TypeScript чи `npm ci` не потрібні. Встановлення з репозиторію та пряму реєстрацію через Codex CLI також наведено нижче.

Версія випуску — `1.1.0`; [примітки до випуску](release-notes.uk.md) окремо відстежують розповсюдження npm. Докази роботи нативного хоста стосуються перевіреного поєднання Codex і платформи; решта [перевірок кваліфікації випуску](next-actions.uk.md) залишається відкритою.

## Codex Cloud

Для хмарної задачі див. [Запуск APEXREST у Codex Cloud](codex-cloud.uk.md). Посібник містить CLI-bootstrap із закріпленою версією, скрипти setup/maintenance й налаштування ORDS HTTPS для Linux-контейнера, включно з приватними обліковими даними та proxy/CA. Наведені далі інструкції desktop-реєстрації й панелі стосуються нативних хостів; приклад Cloud використовує CLI.

## Встановлення з npm

Використовуйте Node 24 LTS (підтримуваний діапазон: Node 24–26). Встановіть [apexrest](https://www.npmjs.com/package/apexrest) з npm. Стабільний випуск npm `latest` — `1.1.0`; наведені нижче команди використовують `latest`. Стан розповсюдження й перевірок — у [примітках до випуску](release-notes.uk.md).

Встановіть CLI глобально та перевірте версію:

```sh
npm install -g apexrest
apexrest --version
apexrest
```

Остання команда відкриває термінальне меню. Виберіть **Install tools** для відсутніх залежностей, потім **Install plugin**, щоб зареєструвати APEXREST у Codex. npm встановлює CLI й комплектні ресурси; реєстрація плагіна є окремою дією меню.

Для локального встановлення в проєкті:

```sh
npm install apexrest
npx apexrest --version
npx apexrest
```

`npm install -g apexrest` встановлює стабільний випуск npm `latest` (1.2.0). Щоб зафіксувати версію, використовуйте `npm install -g apexrest@1.2.0` або `npm install -g apexrest@1.3.0-beta.1` для бети. Наведене нижче встановлення з репозиторію також доступне.

## Встановлення через термінал

Маючи Git і Node 24 LTS у PATH, відкрийте TUI без локального збирання:

```sh
git clone https://github.com/apexrest-dev/apexrest-codex.git
cd apexrest-codex
node plugins/apexrest-apex/runtime/apexrest.mjs
```

Якщо копія репозиторію вже є, перейдіть до неї й виконайте лише останню команду. Після власних змін коду оновіть готовий пакет через `npm run plugin:sync`.

Головний екран показує логотип APEXREST і сім дій:

Вибір **SQLcl mode: CLI / MCP** зберігає спосіб виконання Oracle-команд: SQLcl CLI або офіційний SQLcl MCP (`sql -mcp`). Це окрема дія TUI; вона не змінює реєстрацію плагіна. Див. [режими SQLcl](tui.uk.md#режим-sqlcl-cli-або-mcp).

| Дія                          | Для чого                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------- |
| Install tools                | Встановити керовані Node.js, Java, SQLcl, Playwright і Chromium.                         |
| Uninstall tools              | Видалити записані керовані інструменти зі збереженням зовнішніх середовищ виконання.     |
| Install plugin               | Зареєструвати плагін у Codex із наявним середовищем виконання та створити засіб запуску. |
| Uninstall plugin             | Прибрати керовану реєстрацію й файли плагіна.                                            |
| List saved SQLcl connections | Показати назви безпосередньо зі сховища SQLcl.                                           |
| Test saved SQLcl connection  | Вибрати збережене з’єднання й перевірити доступ до бази.                                 |
| SQLcl mode: CLI / MCP        | Вибрати SQLcl CLI або офіційний SQLcl MCP для нових Oracle-операцій.                     |

Панель APEXlang на головному екрані показує комплектні типи елементів і компонентів у таблиці з пошуком. Tab перемикає дії й каталог; вводьте назву або групу для фільтрації. Перегляд не потребує встановлених інструментів чи з’єднання з базою. Див. [посібник термінала](tui.uk.md#панель-apexlang).

Виберіть **Install tools**, прочитайте [умови Oracle](https://www.oracle.com/downloads/licenses/oracle-free-license.html) і увімкніть **Accept Oracle license terms**, якщо погоджуєтеся. Залиште **Skip browser installation** вимкненим для браузерних інструментів або увімкніть для їх пропуску. Ctrl+R відкриває **Review**, Enter виконує встановлення. Дозвіл системних пакетів браузера є окремим додатковим параметром.

Потім виберіть **Install plugin** і натисніть Enter на **Review**. Дія використовує наявне середовище виконання та не встановлює інструменти повторно. Для іншого профілю Codex, джерела пакета або керованого каталогу натисніть Esc і розгорніть параметри через Ctrl+O. Якщо інструменти встановлено в нестандартний каталог, виберіть той самий **Managed tools directory** для плагіна.

У TUI немає **Preview only** і **Approve changes**: остаточне натискання Enter виконує дію. Згода з ліцензією й системними пакетами залишається окремою. Прочитайте результат та незавершені дії, перезапустіть Codex і почніть нову задачу. Далі налаштуйте [засіб запуску в PATH](#використання-cli) і [перевірте з’єднання](#підключення-й-налаштування).

## Встановлення плагіна

У терміналі, де доступні Node 24 і Codex CLI:

```sh
node --version
codex --version
codex plugin marketplace add apexrest-dev/apexrest-codex
codex plugin add apexrest-apex@apexrest
codex plugin list --json
```

Нативне встановлення перевірено з Codex 0.154.0, Node 24.21.0 та macOS arm64; [звіт нативного встановлення](evidence/native-repository.json) фіксує точне джерело й обсяг перевірки.

Це реєструє marketplace `apexrest` із репозиторію та його плагін `apexrest-apex` у вибраному профілі Codex. Після встановлення почніть нову задачу Codex і надайте запит:

> Скористайся APEXREST, щоб перевірити моє налаштування. Виклич doctor плагіна й окремо оціни доступність нативних інструментів, готовність компілятора та підключення до бази даних. Допоможи завершити відсутні локальні налаштування, не запитуючи паролів у чаті.

Перевірте фактичний результат `apexrest_doctor`. Успішна реєстрація чи запис у списку самі по собі не доводять запуск MCP, компіляцію SQLcl або доступність цілі. Нативний пакет не завантажує залежності під час запуску MCP і не потребує вручну доданого глобального MCP-сервера.

Адміністратор керованого робочого простору може обмежувати доступність плагінів. Наведені CLI-команди виконують локальну нативну реєстрацію, а не розгортання для всієї організації. Якщо хост не надає інструментів, див. [усунення несправностей](troubleshooting.uk.md).

### Усі функції в меню плагіна Codex

Надішліть `Use $apexrest-menu` у полі повідомлення Codex. Навичка **All functions** показує меню в розмові; плагін не додає постійну кнопку APEXREST у бічну панель або верхнє меню.

Щоб знайти встановлений плагін у настільному застосунку, відкрийте **Plugins**, перегляньте список **Installed** і знайдіть **APEXREST for Codex**. Поточний [офіційний посібник плагінів](https://learn.chatgpt.com/docs/plugins) пропонує вводити `@` у полі повідомлення для вибору плагіна або його навички; шукайте APEXREST або **All functions**. У Codex CLI використовуйте `/plugins` для плагінів і `/skills` або `$` для навичок, як описано в [офіційному посібнику навичок](https://learn.chatgpt.com/docs/build-skills). Якщо потрібного пункту немає у списку вибору, надішліть прямий запит вище. Після оновлення плагіна почніть нову задачу; якщо список навичок залишається застарілим, перезапустіть Codex. Нативне виявлення назв і запитів навичок не підтверджує їхнього видимого розташування в кожному інтерфейсі Codex.

Меню в розмові скеровує до кожного наведеного нижче сценарію. Кожен сценарій також має власну зрозумілу назву навички та початковий запит:

| Пункт меню               | Функції                                                                               |
| ------------------------ | ------------------------------------------------------------------------------------- |
| APEX work                | Реалізувати й перевірити зміну безпосередньо в поточному чаті Codex                   |
| Install dependencies     | Java, SQLcl, Node.js, Playwright і Chromium; перегляд та офлайн-параметри             |
| Setup and connections    | Діагностика інструментарію, локальні посилання з’єднань і обслуговування плагіна      |
| Projects                 | Створення, прийняття та огляд проєктів                                                |
| APEX applications        | Генерація, редагування, експорт, валідація й порівняння застосунків; довідки Oracle   |
| Database and PL/SQL      | Читання метаданих, проєктування схеми та планування міграцій                          |
| Deployment and recovery  | Планування, дозволений імпорт, стан і план відновлення                                |
| Tests and browser checks | Налаштовані набори, автентифікація браузера, звіти й перевірка у вбудованому браузері |
| Diagnostics and jobs     | Діагностика збоїв, огляд/скасування завдань і читання артефактів                      |
| Review changes           | Збереження коду, ризики розгортання, безпека й докази випуску                         |

Відкрийте `$apexrest-panel` для налаштувань проєкту й фактичних операцій Oracle/APEX. Використовуйте `$apexrest-work` для реалізації змін безпосередньо в [поточному чаті](chat-workflow.uk.md).

Пункт All functions містить повний індекс CLI-операцій. Непідтримуване розгортання пісочниці явно позначено недоступним. Відкриття меню не виконує його дій. Codex підтримує до трьох початкових запитів на рівні плагіна; повне меню та окремі навички надають доступ до кожного сценарію. Після оновлення плагіна почніть нову задачу Codex, щоб завантажити нові метадані меню.

### Встановлення залежностей із меню плагіна

Виберіть **Install dependencies** у меню навичок плагіна APEXREST або викличте `$apexrest-install-dependencies`. Команда пропонує всі клієнтські залежності, інструменти Oracle без браузера або лише попередній перегляд. Також можна надіслати запит:

> Скористайся $apexrest-install-dependencies, щоб встановити Java, SQLcl та інші клієнтські залежності APEXREST.

Команда запускає вбудований інсталятор перевірених версій Node.js, Java, SQLcl, Playwright і Chromium. Вона показує каталоги та завантаження, зберігає нативну реєстрацію й перевіряє встановлені інструменти. Згода з ліцензією Oracle відокремлена від дозволу встановлювати залежності; коли потрібна згода, Codex показує фактичні умови. Для запуску плагіна Node вже має бути доступним.

Із копії репозиторію та сама команда лише для залежностей доступна без збирання:

```sh
node plugins/apexrest-apex/runtime/apexrest.mjs dependencies install --dry-run --json
node plugins/apexrest-apex/runtime/apexrest.mjs dependencies install --yes --accept-oracle-license --json
```

Виконуйте другу команду лише після прийняття умов Oracle, показаних під час перегляду. Використовуйте `--skip-browser` для інструментів Oracle, `--offline` для встановлення з кешу та `--home` або `--cache-dir` для власних каталогів. Для встановлення системних пакетів браузера потрібен явний `--install-os-deps`. Типовий каталог залежностей — `~/.apexrest` (або `APEXREST_HOME`); власний `--home` також потрібно передати як `APEXREST_HOME` подальшим процесам середовища виконання. Команда не розгортає APEX, не встановлює utPLSQL і не змінює з’єднань із базою даних. Проблеми налаштування браузера та відсутня згода залишаються видимими як невирішені дії.

### Кероване встановлення середовища виконання

Керований інсталятор — альтернатива для перевіреного встановлення Node, Java, SQLcl і Playwright у каталозі користувача. З перевіреної копії репозиторію з Node 24:

```sh
git clone https://github.com/apexrest-dev/apexrest-codex.git
cd apexrest-codex
npm ci --ignore-scripts
npm run build
npm run site:build
npm run release:dry-run
```

Відкрийте `dist/releases/install-local.txt`: він містить точну команду Bash або PowerShell із назвою створеного архіву та SHA-256. Перегляньте її перед запуском. `--yes` дозволяє технічне налаштування; `--accept-oracle-license` є окремою згодою з наведеними умовами постачальника. Інсталятор може повторно використовувати сумісні наявні середовища виконання та типово записує керовані залежності в `~/.apexrest`.

Підтримуються `--dry-run`, `--offline`, `--cache-dir`, `--home`, `--codex-home` і `--native-only`. Увімкнення Codex лише для проєкту на перевіреному хості заблоковане; доступний окремий профіль через `--codex-home`. `--codex` вибирає виконуваний файл Codex для реєстрації та видалення; у Windows shims `.cmd` знаходяться через `PATH` і `PATHEXT`, а шлях чи аргумент із метасимволами cmd.exe відхиляється з `UNSAFE_COMMAND_ARGUMENT`. Попередній перегляд показує наявний інструмент як `found, not probed`, не запускаючи його. Кеш завантажень має належати поточному користувачу й не бути доступним для запису групі чи іншим (`UNSAFE_CACHE_DIRECTORY`). Профіль оболонки не змінюється. Реєстрація використовує ту саму ідентичність плагіна: не залишайте конкурентних встановлень цієї ідентичності в різних marketplace і не додавайте дубль глобального MCP-сервера.

Setup перевіряє вибраний профіль Codex перед завантаженням інструментів. Валідний локальний marketplace, що містить лише очікуваний плагін APEXREST, можна перенести до керованого встановлення навіть без попереднього керованого запису. Попередній перегляд показує це наявне встановлення й заплановане оновлення; `--yes` дозволяє його застосування. Прапорець примусового виконання не потрібен. Для оновлення лише реєстрації з наявним середовищем виконання:

```sh
apexrest setup --native-only --dry-run --json
apexrest setup --native-only --yes --json
```

`--native-only` виключає завантаження інструментів із попереднього перегляду й виконання. Оновлення зберігає попередні файли плагіна та створює резервну копію конфігурації Codex. Сторонній, віддалений або неоднозначний marketplace залишається заблокованим із `MARKETPLACE_OWNERSHIP_CONFLICT`; діагностика вказує його кореневий каталог і профіль Codex. Перегляньте цю реєстрацію або виберіть інший профіль через `--codex-home`. Якщо перерване оновлення залишає невідомий результат, перегляньте збережений запис переходу перед повторною спробою. Обсяг перевірки описано в [стані реєстрації](evidence/setup-registration-local.json).

Локальне пакування створює непідписані бета-артефакти й звітує про готовність. Воно не публікує та не засвідчує стабільний випуск. `npm run release:dry-run` самостійно перезбирає плагін і сайт та приймає незакомічені зміни; `npm run release:package` відмовляється пакувати робоче дерево зі змінами. Середовище виконання постачається одним платформно-незалежним архівом `apexrest-runtime-<version>.zip`.

## Підключення й налаштування

Відкрийте `$apexrest-panel`, потім **Settings → Database network transport**. Виберіть **Direct Oracle listener** або **ORDS HTTP(S)** і збережіть налаштування SQLcl. Цей вибір діє на рівні плагіна для нових операцій у всіх проєктах. У **Connection references** виберіть посилання проєкту для читання чи розгортання та налаштуйте обраний транспорт:

- **Direct Oracle listener:** виберіть **Saved SQLcl connection** з локального сховища й натисніть **Save direct connection**. Список завантажується під час відкриття налаштувань Direct; **Refresh saved connections** оновлює його. Якщо список порожній, збережіть з’єднання інтерактивно в SQLcl. У разі помилки доступна **Retry**; наявне зіставлення залишається доступним, навіть якщо SQLcl не показав його в списку.
- **ORDS HTTP(S):** введіть **ORDS schema URL** схеми, наявні Oracle **Database username** та **Database password**, потім натисніть **Save ORDS connection**. Окремий обліковий запис ORDS не потрібен. Схема має дозволяти REST-enabled SQL, а її псевдонім у URL може відрізнятися від імені користувача бази. Використовуйте URL схеми від адміністратора, наприклад `https://ords.example.invalid/ords/app_user/`, а не URL застосунку APEX. ORDS обирає SQLcl CLI; MCP-інструменти APEXREST у Codex залишаються доступними.

Налаштування ORDS зберігаються локально на рівні плагіна, а пароль — в окремому приватному файлі, поза конфігурацією проєкту та сховищем з’єднань SQLcl. Вводьте його лише в локальній панелі або через CLI `--password-file`; вбудований MCP-режим не надсилає паролів. Порожнє поле зберігає пароль для тих самих URL та імені користувача бази; зміна будь-якого з них потребує пароля нової ідентичності. Перемикання транспорту зберігає обидва налаштування. Посібник [SQL через ORDS](ords.uk.md) містить CLI-команди, правила зберігання та межі перевірки імпорту/експорту.

Для прямих з’єднань термінальні дії **List saved SQLcl connections** і **Test saved SQLcl connection** також завантажують сховище SQLcl без посилань APEXREST. Вводьте текст для пошуку, вибирайте стрілками й натискайте Enter для перевірки; Ctrl+R оновлює список. Результат показує базу, сервіс і схему або фактичну помилку. У TUI немає поля пароля.

Відповідні команди для прямого з’єднання після налаштування засобу запуску:

```sh
apexrest connection list --saved --json
apexrest connection test 'Development connection' --saved --json
```

Замініть `Development connection` точною збереженою назвою. Ці команди з `--saved` використовують прямі з’єднання SQLcl; посилання ORDS перевіряйте через `apexrest connection test dev-read --json` після його налаштування й вибору ORDS.

Для обох транспортів розгортання потребує явних посилань на з’єднання й цільового середовища. За можливості використовуйте окремі з’єднання для читання й розгортання. Налаштувавши обидва посилання, надайте Codex їхні назви та несекретну ідентичність цілі:

> Налаштуй тестове середовище APEXREST із посиланнями на з’єднання `dev-read` і `dev-deploy`. Робочий простір — `YOUR_WORKSPACE`, parsing schema — `YOUR_SCHEMA`, ID застосунку — `YOUR_APPLICATION_ID`, унікальна назва бази даних — `YOUR_DB`, сервіс — `YOUR_SERVICE`, URL застосунку — `https://your-host.example/ords/r/workspace/app/`. Перевір, що з’єднання для читання відповідає цій ідентичності.

Замініть кожен заповнювач справжнім значенням цілі. Конфігурація проєкту зберігає назви посилань на з’єднання, а не паролі. Ініціалізація проєкту не вигадує цільового середовища. Точну схему середовища, приватну політику довіри й дозволені origins тестів описано в [конфігурації](configuration.uk.md).

## Створення або перенесення проєкту

Для нового застосунку використовуйте новий або наявний порожній каталог і відповідний шаблон:

> Скористайся APEXREST, щоб створити порожній застосунок у новому проєкті `sales-app`. Налаштуй визначену тестову ціль, додай дашборд із реальними показниками джерела, потім заверши планування, дозволений імпорт і браузерні перевірки.

Для наявного застосунку:

> Скористайся APEXREST, щоб ініціалізувати проєкт existing-app у новому каталозі `sales-app` і перенести визначений тестовий застосунок. Збережи всі Oracle ID, метадані `.apex`, сторонні сторінки, спільні компоненти й автентифікацію. Додай запитаний дашборд, імпортуй його в той самий застосунок і перевір результат.

Щоб ініціалізувати проєкт existing-app у поточній порожній папці через CLI:

```sh
apexrest project init . --template existing-app
```

Псевдонім проєкту використовує фактичну назву папки. Ініціалізація відхиляє непорожні каталоги, файли й символічні посилання, зберігаючи наявні дані. Ця команда створює локальні файли проєкту; перенесення застосунку залишається окремою операцією.

Перенесення й експорт використовують нові локальні каталоги та завершуються помилкою, якщо перезаписали б локальні зміни. Зберігайте згенеровані метадані Oracle під контролем версій. Для наступних змін використовуйте наявний робочий код; не переносьте застосунок заново щоразу. Див. [наявні застосунки](existing-app.uk.md).

## Редагування, планування, імпорт і перевірка

Плагін один раз оглядає проєкт і конфігурацію цілі, повторно використовує обмежені довідкові матеріали відповідної версії та групує пов’язані зміни коду. Планування включає реальну валідацію компілятором, тому окрема ідентична компіляція безпосередньо перед ним зазвичай зайва.

Перегляньте ціль і обсяг конкретного плану. Він прив’язує код, інструментарій, поточну ціль та історію і діє 30 хвилин. Явний запит створити, оновити чи імпортувати визначений застосунок розробки/тестування дозволяє необхідний імпорт у цих межах. Codex записує наявний дозвіл для точного плану й продовжує без повторного запиту того самого дозволу. Сторонні записи в схему, зміни автентифікації, інші цілі та production не входять у цей обсяг.

Apply перевіряє свіжу ідентичність і розбіжності, створює перевірену SQL-копію наявного застосунку, фіксує незмінний код і використовує стійку координацію. Тривалі операції MCP повертають ID завдання; відстежуйте його до завершення замість повторного запуску операції. Невдалий або невідомий результат запису потребує діагностики чи звіряння перед повторенням.

Для сторінки чи дашборда звірте відповідні вихідні запити лише для читання та огляньте імпортовану поведінку у вбудованому браузері Codex, якщо він доступний. Дочекайтеся завершення завантаження асинхронних регіонів APEX, потім перевірте змінені фільтри, діаграми, дати й порожні стани. Запустіть налаштовані автоматизовані набори, відповідні зміні. Записуйте ручні браузерні спостереження окремо; порожній список наборів не означає успіх автоматизованих тестів. Див. [тестування](testing.uk.md).

## Використання CLI

Глобальне встановлення npm надає команду `apexrest` через глобальний каталог npm `bin` на macOS/Linux або глобальний prefix на Windows; цей каталог має бути в `PATH`. Для локального встановлення запускайте `npx apexrest` із каталогу проєкту. Описаний нижче керований засіб запуску є необов’язковим для користувачів npm.

Запустіть `apexrest` або `apexrest tui`, щоб відкрити логотип APEXREST і сім дій: встановлення/видалення інструментів і плагіна та список/перевірку збережених з’єднань SQLcl. Категорій та інших робочих дій у TUI немає. Див. [посібник термінала](tui.uk.md) щодо клавіш, прямого виконання й обсягу перевірки. CLI `connection list --saved` і `connection test NAME --saved` працюють безпосередньо зі сховищем SQLcl; без `--saved` зберігається попередня поведінка посилань APEXREST. Явні команди зберігають поведінку для скриптів.

Пряме встановлення через `codex plugin add` надає плагін Codex, але не створює керований засіб запуску `apexrest`. У перевіреній копії репозиторію можна запускати CLI безпосередньо через Node 24:

```sh
node plugins/apexrest-apex/runtime/apexrest.mjs doctor --json
node plugins/apexrest-apex/runtime/apexrest.mjs project init ./crm --template customer-crm
```

Дія TUI **Install plugin** і керований setup створюють `~/.apexrest/bin/apexrest` на macOS/Linux або `apexrest.ps1` і `apexrest.cmd` у керованому каталозі `bin` на Windows. Якщо шлях до керованого home, Node.js чи плагіна містить `%`, `!`, `"` або керівні символи, створення засобу запуску Windows відхиляється з `UNSAFE_LAUNCHER_PATH`. Саме встановлення інструментів не створює цього засобу запуску. Для стандартного каталогу на macOS/Linux додайте його до PATH поточної оболонки:

```sh
export PATH="$HOME/.apexrest/bin:$PATH"
apexrest
```

Щоб зберегти це для нових оболонок, додайте рядок `export PATH` до відповідного конфігураційного файла оболонки. APEXREST не редагує його автоматично. У PowerShell запустіть засіб за повним шляхом:

```powershell
& "$env:USERPROFILE\.apexrest\bin\apexrest.ps1"
```

Для нестандартного керованого каталогу використовуйте відповідний `<home>/bin`. Без керованого встановлення команда `node plugins/apexrest-apex/runtime/apexrest.mjs` з копії репозиторію відкриває те саме меню. Якщо встановлення не завершено, перевірте результат перед додаванням неіснуючого шляху до PATH.

У прикладах засіб запуску скорочено до `apexrest`; замініть його повним шляхом або командою Node з репозиторію:

```sh
# Map saved SQLcl connections for the direct transport.
apexrest connection add dev-read --sqlcl-name saved-read-connection
apexrest connection add dev-deploy --sqlcl-name saved-deploy-connection

# These project operations use the selected direct or ORDS transport.
apexrest project inspect --project ./crm --json
apexrest deploy plan --project ./crm --env dev --out plans/dev.json
apexrest deploy apply --project ./crm --plan plans/dev.json
```

Перед операціями з ціллю налаштуйте `environments.dev`, перегляньте проєкт і надайте йому довіру, а також дозволену політику для точної цілі. Шаблон CRM містить зміни схеми й обов’язкові SQL/E2E набори, тому його імпорт потребує відповідних дозволів і залежностей. Для суто діагностичного запуску компілятора використовуйте `apexrest apex validate --project ./crm --json`.

Довідка команд доступна через `--help`; `--help` із невідомою командою завершується з кодом 2. Запити `docs search` можуть складатися з кількох слів без лапок. CLI `apex export` використовує `--output`, а `deploy plan` — `--out`. JSON-вивід містить класифіковані результати й коди завершення. CLI та MCP використовують те саме ядро перевірок.

Викликаючи MCP-інструменти рівня проєкту, передавайте абсолютний каталог проєкту застосунку в аргументі `project`. Нативний сервер запускається в каталозі встановленого плагіна, тому відсутні чи відносні шляхи проєкту відхиляються до початку роботи. CLI-приклади визначають `--project` від робочого каталогу термінала.

## Видалення керованих інструментів і плагіна

Виберіть **Uninstall tools** або **Uninstall plugin** та натисніть Enter на **Review**. Видалення інструментів прибирає лише записані керовані версії; зовнішні середовища виконання, проєкти, резервні копії, з’єднання SQLcl і кеш завантажень зберігаються. Node.js, потрібний засобу запуску або записаному встановленню плагіна, залишається. Системні пакети не видаляються.

Якщо видаляєте обидва компоненти, спершу видаліть інструменти, потім плагін. Прибирання файлів плагіна також прибирає код, на який посилається керований засіб запуску. Щоб зберегти цей код після скасування реєстрації, увімкніть **Keep plugin files** у додаткових параметрах видалення плагіна. Команда з копії репозиторію залишається окремим способом запуску.

Відповідні CLI-команди для видалення обох компонентів:

```sh
apexrest dependencies uninstall --yes
apexrest plugin uninstall
```

Використовуйте той самий керований каталог і `--home`, якщо змінювали його. Для прямої реєстрації без керованого запису встановлення скористайтеся командами Codex нижче. Видалення плагіна утримує блокування встановлення, прибирає лише каталог плагіна, записаний для цього керованого home, і приймає `--codex` для конкретного виконуваного файлу Codex. Видалення не скасовує розгортань у базі даних.

## Видалення плагіна з репозиторію

Для прямого встановлення з репозиторію:

```sh
codex plugin remove apexrest-apex@apexrest
codex plugin marketplace remove apexrest
```

Видаляйте marketplace лише коли його записи більше не потрібні. Після видалення почніть нову задачу Codex. Це скасовує реєстрацію нативного плагіна; воно не є запитом видалити проєкти застосунків, резервні копії, облікові дані SQLcl або стійку історію розгортань. Кероване встановлення має власну команду `apexrest plugin uninstall` із перевірками належності.

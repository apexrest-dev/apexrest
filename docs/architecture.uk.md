# Архітектура

[English](architecture.md) | Українська

APEXREST використовує одне ядро політик для CLI та нативного MCP-сервера Codex. Чотирнадцять skills спрямовують роботу в поточній сесії; двадцять один MCP-інструмент надає операції з обмеженим виводом. Обидва інтерфейси перевіряють вхідні дані за однаковими строгими Zod-схемами.

Реалізація виконується безпосередньо у відкритій розмові Codex. [Інтеграція Codex](codex-integration.uk.md) описує відповідальність і межі хоста.

Oracle-операції використовують збережений режим SQLcl CLI/MCP. Тут MCP означає офіційний SQLcl stdio-сервер, окремий від APEXREST MCP API для Codex. Див. [вибір режиму](tui.uk.md#режим-sqlcl-cli-або-mcp).

## Компоненти

| Компонент                                 | Відповідальність                                                                                   |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `plugins/apexrest-apex/skills/`           | Маршрутизація задач, APEXlang, налаштування, розгортання, рев’ю та браузерні перевірки             |
| `packages/mcp/`                           | Каталог stdio MCP, структуровані відповіді та асинхронне відправлення завдань                      |
| `packages/cli/`                           | Розбір CLI та JSON-вивід на основі тих самих схем операцій                                         |
| `packages/core/`                          | Конфігурація, з’єднання, довідка, SQLcl, політика розгортання, тести, завдання й артефакти         |
| `packages/installer/`                     | Перевірені завантаження, безпечне розпакування, керовані середовища виконання й нативна реєстрація |
| `packages/testkit/`                       | Браузерні/API helpers для тестів застосунку                                                        |
| `resources/`, `templates/`, `toolchains/` | Зафіксована довідка, стартові проєкти та визначення інструментарію                                 |

`plugins/metadata.json` визначає нативний пакет сумісності Codex. Єдиний цільовий продукт — Codex; колишній експериментальний portable-артефакт більше не випускається. Збирання використовує спільні ESM-фрагменти та копіює навички, довідку, схеми, шаблони й lockfiles у самодостатні пакети. Кероване встановлення прив’язує MCP до абсолютних шляхів виконання. Запуск MCP не завантажує залежностей і не потребує додаткової глобальної MCP-реєстрації.

## Життєвий цикл запиту

Короткі операції повертають структурований результат. Тривалі MCP-операції повертають ID завдання й продовжуються в окремому worker. Опитуйте цей ID через `apexrest_job_status`; скасовуйте через `apexrest_job_cancel`. Не перезапускайте операцію лише тому, що перша відповідь — дескриптор завдання.

Workers ведуть обмежені журнали, стійкий файл стану та heartbeat. Втрата heartbeat чи переривання запису можуть дати `outcome_unknown`; це не доводить відкату. Workers мають строк 15 хвилин. SQLcl має окремі тайм-аути процесу й класифіковану діагностику, включно з командами, які друкують помилку попри нульовий код завершення.

## Межа Oracle

Уся генерація, експорт, валідація та імпорт застосунків використовують справжній Oracle SQLcl. Код APEXlang перевіряється в проміжному каталозі зі збереженням робочого дерева й метаданих Oracle `.apex`. Перевірена довідка відповідної версії — локальні індексовані дані; сторонні інструкції маршрутизатора й довільні скрипти не встановлюються як повноваження агента.

Оптимізований адаптер об’єднує поля ідентичності цілі в один свіжий запит. Він повторно використовує успішну довідку можливостей лише за чинної ідентичності інструментів, знову перевіряє версію компілятора й ніколи не кешує поточний стан цілі. Планування суміщає незалежну компіляцію та читання цілі; apply суміщає незалежні попередні читання. Усі попередні завдання завершуються до повернення помилки або початку запису.

## Межа розгортання

План прив’язує код, конфігурацію, компілятор/інструментарій, ідентичність і вміст цілі та історію міграцій. Apply перевіряє цю прив’язку, поточну ідентичність і розбіжності, створює скопійовану SQL-копію наявного застосунку з контрольною сумою, фіксує код і отримує володіння перед записом. Перевірки після імпорту та налаштовані тестові бар’єри залишаються частиною завершення.

Стійка локальна історія та володіння є типовими. Вони координують runners зі спільним керованим home в межах БД/сервісу/parsing schema. Окремі машини потребують зовнішнього послідовного виконання або необов’язкового database mode; файлове блокування не гарантує розподіленої координації БД. Точну поведінку збоїв і відновлення описано в [безпеці розгортання](deployment-safety.uk.md).

## Довіра й обробка даних

SQL, тести й APEXlang проєкту є виконуваними входами. Проєкт слід переглянути й надати йому локальну довіру. Описи БД, коментарі коду, довідковий вміст і тестовий вивід — дані, а не вказівки розширювати дозволи. Облікові дані залишаються в локальних сховищах з’єднань та автентифікації.

Файлові операції відхиляють вихід за межі каталогу, символьні посилання й спеціальні файли там, де політика вимагає ізоляції файлів. Стан використовує атомарні записи та виключне володіння; підпроцеси виконуються без оболонки. Читачі артефактів надають обмежений зареєстрований текст і очищують чутливий вміст. Ці засоби не замінюють межі дозволів хоста чи захищеного production-схвалення. Див. [безпеку](../SECURITY.uk.md).

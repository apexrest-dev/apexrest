# Тестування та перевірка

[English](testing.md) | Українська

Вибирайте перевірки, що підтверджують змінену поведінку, і записуйте те, що справді виконано. Модульні фікстури, валідація компілятором, результати підключеного Oracle, виявлення нативним Codex і браузерні спостереження — різні класи доказів.

## Локальні перевірки розробки

| Команда                   | Що підтверджує                                                           |
| ------------------------- | ------------------------------------------------------------------------ |
| `npm run lint`            | Форматування й домовленості щодо коду                                    |
| `npm run typecheck`       | Узгодженість TypeScript                                                  |
| `npm run test:unit`       | Поведінку ядра та позначені фікстури збоїв/конкуренції                   |
| `npm run test:contracts`  | Реальні контракти CLI та stdio MCP без твердження про підключення Oracle |
| `npm run test:installers` | Фікстури завантаження, архівів, цілісності й платформ                    |
| `npm run test:packaging`  | Схеми зібраних пакетів, ізоляцію вмісту, виконання й сайт                |
| `npm run site:build`      | Локальну генерацію сайту документації                                    |

Виконайте `npm run build` перед перевірками, що використовують `dist/`. [Стан реалізації](implementation-status.uk.md) фіксує датовані результати; перелік команд не означає, що всі поточні платформи випуску або сценарії Oracle пройдені.

## Перевірки нативного хоста й Oracle

`npm run test:repository-plugin` встановлює комплектний плагін в ізольований профіль Codex і перевіряє реєстрацію та роботу встановлених CLI/stdio MCP. Це не викликає модель і не доводить відображення desktop чи нативне виявлення інструментів усередині розмови; такі спостереження потребують справжньої сесії хоста.

`node scripts/oracle-smoke.mjs` виконує генерацію й валідацію встановленим SQLcl без з’єднання з базою даних. Він записує реальний вивід компілятора та MMD для порожнього й CRM-шаблонів. Це не підтверджує успішного імпорту в БД.

`npm run test:integration` потребує всього наведеного:

- `APEXREST_INTEGRATION_PROJECT` і `APEXREST_INTEGRATION_ENV`, що визначають перевірений тестовий проєкт.
- Наявних іменованих з’єднань SQLcl, явної довіри проєкту та політики цілі.
- Підтримуваної цілі APEX 26.1+ і залежностей вибраних наборів, зокрема utPLSQL для SQL-набору.
- `APEXREST_INTEGRATION_ALLOW_WRITES=true` до будь-якого apply, з окремо дозволеним обсягом змін.
- Локальної інтерактивної браузерної автентифікації та окремого тестового користувача, коли потрібен E2E.

Інтеграційний runner відхиляє production. Віддалені тестові набори також відхиляються для будь-якої цілі, класифікованої як production, зокрема для цілей, указаних в адміністраторському `production-trust.json`. Відсутні передумови дають заблокований доказ і код завершення 3, а не успішний пропуск. Типова локальна координація розгортання не потребує службових таблиць. Повна матриця випуску також включає відновлення й ін’єкцію збоїв поза успішним основним сценарієм runner.

## Зміни лише застосунку

Для зміни сторінки чи дашборда виконайте валідацію справжнім Oracle-компілятором, звірте вихідні запити дозволеними перевірками лише для читання та огляньте імпортовану сторінку у вбудованому браузері Codex, якщо доступний. Планування вже виконує валідацію; уникайте ідентичного окремого запуску безпосередньо перед ним, якщо не діагностуєте зміну коду чи збій.

CRUD та utPLSQL потрібні, коли цього вимагає зміна або налаштований обсяг наборів. Явно дозволений ізольований профіль лише застосунку може не мати автоматизованих наборів і записувати вихідні/браузерні перевірки окремо. Збережіть усталений профіль та історичні невдачі. Немає налаштованих наборів — автоматизовані SQL/E2E тести не запускалися.

## Перевірка у вбудованому браузері

Для видимих користувачеві змін застосунку використовуйте вбудований браузер Codex, коли доступні він і розгорнута ціль. Дотримуйтеся [браузерного правила плагіна](../plugins/apexrest-apex/skills/apexrest-test/SKILL.md#in-app-browser-verification).

Огляньте змінену сторінку, дочекайтеся завантаження відповідних асинхронних регіонів, потім перевірте змінені елементи керування й навігацію. Для дашбордів перевірте діапазони дат, передавання фільтрів, оновлення діаграм, звірені значення й реальний порожній стан. Для форм перевірте відповідну валідацію, збереження та скасування. Огляньте макет на розмірах екрана, відповідних зміні.

Зберігайте браузерні спостереження окремо від автоматизованих тестів. Відсутній доступ, незавершену автентифікацію чи недоступну розгорнуту зміну записуйте як відсутню перевірку з причиною. Екран входу або тимчасове завантаження діаграми не доводять ні працездатності, ні несправності готової функції.

## Автоматизовані тести застосунку

SQL runner читає справжній JUnit-вивід utPLSQL і рахує виконані тестові випадки. Відсутній utPLSQL — `dependency_missing`. SQL-тести можуть містити лише SQL та PL/SQL: до будь-якого звернення до Oracle рядок, який SQLcl може сприйняти як клієнтську команду, наприклад `host`, `@`, `spool` або `connect`, блокує запуск із `SQL_TEST_SCRIPT_CONTROL`. У режимі CLI кожен тестовий скрипт виконується в сесії SQLcl, запущеній із `-R 2`. CRM-фікстура перевіряє прийнятих клієнтів, відсутнє ім’я, некоректні email/status і дубль email.

Браузерна фікстура використовує унікальний синтетичний запис, перевіряє некоректний ввід, виконує create/read/update/delete і прибирає власні дані. Її селектори потрібно перевірити на розгорнутому застосунку. API-набори використовують Playwright request tests і захищений helper testkit з явними allowed origins. Фіктивна HTTP-точка не подається як реальний тест APEX.

Автентифікуйтеся локально через `apexrest test auth --project ./crm --env dev`. Стан автентифікації приватний і діє вісім годин. Інтерактивний вхід використовує звичайний браузер без записування. Збереження стану не доводить його працездатності: обов’язковий E2E усе ще має перевірити маркер застосунку та свої твердження. Перевірка origins є запобіжником, а не мережевою пісочницею ОС для довіреного тестового коду.

## Діагностика й повторний запуск

Класифікуйте збій, прочитайте обмежений діагностичний артефакт та огляньте відповідний код чи залежність. Зробіть одне цільове виправлення, повторіть відповідну перевірку компілятора/тесту, потім обов’язкову перевірку якості. Не повторюйте виявлення, експорт чи повні імпорти без доказів їхньої необхідності.

Після трьох невдалих виправлень тієї самої причини повідомте докази й невирішену залежність. Не послаблюйте дозволи, не прибирайте обов’язкових наборів і не замінюйте змістовних тверджень заради успіху. Для запису з невідомим результатом виконайте [звіряння](deployment-safety.uk.md) перед будь-яким повторенням.

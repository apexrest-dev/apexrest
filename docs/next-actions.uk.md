# Наступні дії та межі перевірки

[English](next-actions.md) | Українська

## Завершити локальне приймання Composer

Закрити локальні прогалини з [аудиту](composer/audit.uk.md): shared resources і consumers ownership; повну contract/compatibility evidence policy; нормалізацію captured source у виконувані блоки; deployment fault/property coverage і порівнювані workflow benchmarks. Успішні наявні тести самі по собі не закривають roadmap.

## Composer runtime acceptance

Зберігайте регресійні перевірки повторного огляду при розширенні adapters: вкладені mappings мають залишатися детермінованими, переходи ownership мають враховувати consumers у результуючому source, а recovery/retry панелі — зберігати точну ідентичність операції.

Окремо погодьте exact DEV target, fixture DDL/DML, metadata, app mapping/import і authenticated browser qualification. Перевірте create/edit/cancel, stale version, denied roles, scoped reads, saved/refresh payloads і narrow screens. G4 та залежні release gates залишаються відкритими. У новому Codex-чаті перевірте завантаження Composer tools/skill; beta CI пройшов на macOS, Ubuntu та Windows, але не доводить виконання нативного хоста. Зберігайте [Composer ledger](composer/ledger.json) та [local evidence](evidence/composer-local.json).

## Connected-перевірка робочої копії

[Зміну робочої копії](existing-app.uk.md) включено до бета-випуску `1.3.0-beta.1`. Зберігайте [локальні докази перевірок](evidence/working-copy-checks.json) та [узгоджені fixture-вимірювання](evidence/working-copy-local.json); fixtures не доводять поведінку Oracle.

- На окремо дозволеному наявному DEV/test-застосунку виконайте початковий APEXlang + SQL sync, три цикли локального edit/plan/apply з перезапуском між ними й перевірте справжні лічильники експорту/імпорту, ідентичність, required suites та автентифікований браузер. Зараз ці перевірки — NOT RUN; історичні цілі не є дозволом.
- Окремо перевірте початкове SQL-відновлення з прив’язкою до checksum і точним дозволом. Перевірте invalidation перед записами й фактичний відновлений стан; проміжні snapshots не дають автоматичного відкату.
- Перевірте справжні lost-response/crash reconciliation та необов’язкову DB-координацію зі збереженням невідомого ownership і без повторів до звірки. Перевірте сумісність запиту метаданих на підтримуваних версіях APEX і цілях direct SQLcl/ORDS; незмінні метадані зберігають припущення одного редактора.
- Перевірте connected-сценарії робочої копії в панелі на дозволеній цілі. Локальне оновлення Composer та in-app Catalog checks зафіксовані окремо; завантаження tools у новому чаті залишається відкритим.
- Для тверджень про tokens/cost або продуктивність Oracle виміряйте узгоджені connected цикли зі справжніми usage counters. Локальний час, кількість викликів та UTF-8 bytes залишаються окремо позначеними.

## Бета-випуск 1.3.0-beta.1

[Запис публікації](evidence/npm-130-beta1-publication.json) підтверджує npm-тег `beta`, цілісність архіву та чисті локальне й глобальне встановлення. `latest` залишається на стабільному випуску 1.2.0. Далі перевірте встановлений плагін у новому чаті Codex та завершіть підключені перевірки Oracle; бета-пакет не закриває roadmap Composer.

## Випуск 1.2.0

Цілісність пакета в реєстрі та чисті локальне й глобальне встановлення `apexrest@1.2.0` з npm `latest` підтверджено в [записі публікації 1.2.0](evidence/npm-120-publication.json). Використовуйте [поточні докази каталогу](evidence/pattern-catalog-local.json) та [примітки до випуску](release-notes.uk.md) для точних перевірок і стану розповсюдження. [Запис попередньої публікації 1.1.0](evidence/npm-110-publication.json) залишається історичним доказом. Після оновлення перевірте встановлений плагін у новій розмові Codex. Узгоджуйте метадані npm, комплектний нативний bundle і канонічні джерела GitHub; чисте встановлення з реєстру не доводить поведінку desktop або коректність Oracle.

## Підтримка каталогу патернів

- Узгоджуйте [каталог патернів](pattern-catalog.uk.md), skill його наповнення й інші 12 skills із пакетом 1.2.0. Перевірка джерел/збірки чи публікація npm не є оновленням встановленого кешу.
- Зберігайте повний огляд усіх 150 захоплених сторінок і 818 варіантів обох джерел. Для оновлень використовуйте сталі ID, явну заміну та `sourceReviews`, прив’язані до `provenance.sha256` кожної сторінки; повторно перевіряйте змінені сторінки та їхні змістовні варіанти. Перед пакуванням відхиляйте відсутні/застарілі огляди, патерни без згадок у них, невідомі source anchors, конфлікти ID і застарілі докази рецептів.
- Зберігайте докази компіляції всіх 69 готових рецептів, зокрема 56 доповнень, і повторно перевіряйте змінені вхідні файли. Зберігайте видимими 15 unresolved-варіантів/концепцій; готовність за компілятором не доводить поведінки після розгортання.
- Перевірте SQL адаптованих патернів, імпорт і браузерну взаємодію на окремо дозволеній цілі. Компіляція каталогу не встановлювала необов’язкові SQL-fixtures форм; самі форми джерела не демонструють робочий DML.
- Залишайте неналаштованого AI-провайдера й порожні концепції master-detail unresolved, доки їхні залежності та поведінку не буде реалізовано й перевірено. Власні варіанти навігації та вибору/оновлення для списку й дерева визначають власні контракти; вони не доводять еквівалентності кожній JavaScript-взаємодії джерела. Явно зберігайте неактивні дії `#` та непідтримані розширення.

## Підключені та платформні перевірки

- Для [каталогу компонентів](component-catalog.uk.md) перевірити адаптовані рецепти в окремо дозволеному DEV-застосунку. Записати докази SQL-запитів, імпорту й браузера окремо від офлайн-компіляції; довідковий додаток лишається джерелом лише для читання. Публікація npm не підтверджує поведінку застосунку під час виконання.

- Перевірте змінені імпорти APEX, збереження компонентів/статичних файлів/MMD і SQL restore на явно дозволеній тестовій цілі з ідентичністю джерел/цілі та перевіреними backup.
- Запишіть реальні докази переривання бази, з’ясування втраченої відповіді й координації. Окремі homes/машини потребують зовнішньої серіалізації або явно налаштованої координації бази.
- Виконайте непорожні налаштовані utPLSQL, API та автентифіковані тести застосунку; перевірте змінені сторінки в обраному браузері. Відсутні набори чи доступ — обмеження, а не успіх.
- Оновіть спостереження встановлення, виявлення й панелі/браузера для поточних підтримуваних хостів Codex. Linux, Windows і WSL2 зберігають задокументовані прогалини до фактичної перевірки.
- Порівняйте зіставні завдання за фактичними лічильниками Codex, якщо потрібні твердження про токени чи наскрізну затримку. Локальні байти UTF-8 і кількість інструментів вимірюють лише обсяг даних та інтерфейсу.

## Збереження обсягу

[Матриця приймання](acceptance.json) фіксує, які старі вимоги вилучено. Не повертайте оркестрацію сесій плагіна для задоволення історичних вимог. Початкова специфікація збірки й попередні JSON-звіти залишаються походженням доказів; поточний продукт працює у відкритій сесії Codex користувача.

Зберігайте довіру проєкту, явний обсяг змін, production approval, backup, drift, обов’язкові набори й відновлення невідомих результатів. Не змінюйте живу ціль Oracle лише для закриття прогалини доказів без чинного дозволу.

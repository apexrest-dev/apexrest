## Single-editor working copies

For an existing development/test application, explicit `apex sync --env dev --action init` selects the [working-copy workflow](existing-app.md). Initial synchronization verifies identity, takes one APEXlang baseline and one checksummed SQL backup under deployment coordination, and compares metadata before/after export. Ordinary status/panel refresh reads local files only. Ready state persists across chats/restarts; source-directory/root/target/toolchain changes require explicit re-establishment. The baseline and latest applied sources are private durable snapshots outside ordinary result retention.

New plans use schema v2: `mode: full-export|working-copy`, `backupStrategy: fresh-export|initial-backup`. Working-copy plans bind sync ID/revision, baseline/checkpoint digests and initial backup ID/checksum. They read fresh target identity, update metadata and migration history, compile current sources and include added/deleted security files in risk review. Apply keeps authorization, plan expiry, source freezing and fresh checks under deployment ownership. It verifies the initial SQL copy without exporting, durably records `importing` before writes and advances the successful checkpoint only after identity verification and all established required suites pass. Two plans from one revision cannot both apply. v1 plans remain accepted on the old path; active sync requires a new bound v2 plan.

`LAST_UPDATED_ON`/`LAST_UPDATED_BY` are read with explicit server formatting; null stays null and query errors block. [Oracle documents the metadata fields](https://docs.oracle.com/en/database/oracle/oracle-rest-data-services/25.3/orrst/op-apex-applications-application_id-get.html). Changed values block as possible external edits. Unchanged/null metadata is not complete component drift control: the user explicitly accepts a single editor. DB operations are incompatible with active working-copy plans; explicit invalidate returns to the full path. Production and new applications keep that path.

A confirmed import with failed verification is `verification_failed`, retaining the old successful checkpoint. A lost response, interrupted write or local persistence failure after mutation is blocked as `outcome_unknown`; leftover `importing` also requires reconciliation. Invalidate never removes unknown ownership. Explicit status reconciliation may export for diagnosis and never grants retry permission. Baseline restore uses the existing separate backup-bound plan, fresh safeguards and exact approval; old sync becomes invalidated before the restore write starts. Restoring each intermediate import is outside this version. Interrupted local source installation also leaves a blocked durable record for inspection rather than advertising a partially installed ready copy.

The full-export behavior described below continues for projects without active sync and for separate restore plans. Current local [measurements](evidence/working-copy-local.json) establish export counts and filesystem behavior with fixture Oracle methods only; connected imports, browser acceptance and restore are NOT RUN for this change.

The 2026-09-12 user amendment treats an explicit create/update/import request for an identified development/test application as authorization for the necessary scoped import. After reviewing the concrete plan, the agent may record the existing instruction as a short-lived local deploy grant bound to the exact project, target and plan; preserve unrelated policy, retain the authorization record, and remove that grant after the attempt. Do not ask the same permission twice or stop at a plan. This records consent already given and does not invent consent, authorize unrelated database writes, or replace protected production signatures. Identity, SQL backup, drift, coordination, source freezing and unknown-outcome handling remain mandatory.

Application-only verification may use an explicitly authorized isolated profile with compiler, real read-only SQL reconciliation and in-app browser observations, while retaining the original required-suite profile and its historical results. No configured automated suites means none ran, not that SQL/E2E passed. See the [test skill](../plugins/apexrest-apex/skills/apexrest-test/SKILL.md#application-only-verification-scope).

Deploy works on a clean supported APEX installation without APEXREST service tables. The default environment mode is `deploymentControl: "local"` (also used when omitted). It stores immutable migration history and schema ownership under `$APEXREST_HOME/deployment-control/`; no service-table query or DDL occurs in this mode. Separate read and deploy connection references allow least privilege.

`deploy plan --env dev --out plans/dev.json` reads exact database unique name, service, schema, workspace and application identity, exports target content, hashes sources/configuration/toolchain and validates with the real compiler. Plans expire after 30 minutes. Planning exports to local staging but never imports to the DB. Full application imports include pages and shared components; a one-page change is still a full import. Unsupported components must be blocked by the real compiler; coverage is not universal.

`deploy apply --plan plans/dev.json` revalidates the plan and external policy, current target and compiler. Existing targets get a copied, checksummed SQL export before any application or schema writes. After a second drift check, sources are frozen and checksummed. Ordered immutable migrations persist a `started` record before executing (local file by default, DB row in optional database mode); changed checksums or unresolved outcomes block future plans. Package scripts execute after migrations. SQLcl's first error stops execution; DDL is not assumed transactional.

Local mode serializes runners sharing one managed home for the same DB/service/parsing schema, including different apps in that schema. A confirmed dead same-host owner can be reclaimed only while preparing. Writing ownership is retained after an unknown outcome and never automatically reclaimed after a crash. The plan binds its backend, scope and local store identity. Preserve the deployment-control directory: a new machine or deleted history cannot infer previously applied migrations from Oracle. Use one durable deployment runner/home and externally serialized CI for multiple machines, or explicitly select the database mode. Local filesystem locks are not a distributed database guarantee.

Optional `deploymentControl: "database"` retains the existing DB journal and row lease. Only this explicitly selected mode needs the reviewed `templates/database-control/install.sql` tables. Setup never creates them. Its heartbeat is 20 seconds and TTL 90 seconds, and only expired preparing leases may be reclaimed. The original cross-runner DB implementation still needs actual concurrent Oracle verification. There is no silent fallback from a selected database mode, which could otherwise discard migration history.

The app is imported with explicit workspace/schema/ID, identity verified and required suites executed. Any empty/skipped/blocked required suite fails the gate. On cancellation, timeout or lost lease after write, the result is `outcome_unknown`; no automatic reapply occurs. `deploy status --run UUID` reads target/export/history for reconciliation and never turns uncertainty into success.

utPLSQL is a dependency only when a SQL test suite is selected/required. Application-only projects can deploy without it; do not remove genuinely required test suites to make an existing gate green. Clean APEX support changes control storage, not authorization or quality requirements. Plans created before the coordination field was introduced must be regenerated.

`deploy restore-plan --backup UUID --out plans/restore.json` verifies the backup and current target, creates a new plan, and requires a grant for that exact digest. Apply creates a new backup, then restores one complete non-split `f<ID>.sql` Oracle export with explicit install target. Split/unknown layouts are blocked. This restores APEX metadata only; business data and destructive schema changes require separate DBA recovery. General destructive/privileged/authentication changes stay blocked pending an explicit recovery workflow.

Production requires `CI=true`, `APEXREST_APPROVAL_FILE` and `APEXREST_APPROVAL_PUBLIC_KEY_FILE` on a protected runner. An external Ed25519 signature covers canonical JSON containing `planDigest`, `targetDigest`, `expiresAt`, `reviewer`. The repository cannot supply or modify the runner's verification key. `approved=true` is rejected by strict schemas. No agent-facing operation signs approvals.

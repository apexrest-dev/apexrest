# Deployment and recovery

## Single-editor working copies

For an existing development/test application, explicit `apex sync --env dev --action init` selects the [working-copy workflow](existing-app.md). Initial synchronization verifies identity, takes one APEXlang baseline and one checksummed SQL backup under deployment coordination, and compares metadata before/after export. Ordinary status reads (`apexrest_apex_sync` `action:status`, `apexrest_status`) use local files only. Ready state persists across chats/restarts; source-directory/root/target/toolchain changes require explicit re-establishment. The baseline and latest applied sources are private durable snapshots outside ordinary result retention.

Legacy full-import plans use schema v2 (Composer bindings use v3): `mode: full-export|working-copy`, `backupStrategy: fresh-export|initial-backup`. Working-copy plans bind sync ID/revision, baseline/checkpoint digests and initial backup ID/checksum. They read fresh target identity, update metadata and migration history, compile current sources and include added/deleted security files in risk review. Apply keeps authorization, plan expiry, source freezing and fresh checks under deployment ownership. It verifies the initial SQL copy without exporting, durably records `importing` before writes and advances the successful checkpoint only after identity verification and all established required suites pass. Two plans from one revision cannot both apply. v1 plans remain accepted on the old path; active sync requires a bound working-copy plan. [APEX 26.2 plans](apex-26.2.md) use v4 with explicit selection, fresh server/SQL exports and verified server checkpoints for partial imports.

`LAST_UPDATED_ON`/`LAST_UPDATED_BY` are read with explicit server formatting; null stays null and query errors block. [Oracle documents the metadata fields](https://docs.oracle.com/en/database/oracle/oracle-rest-data-services/25.3/orrst/op-apex-applications-application_id-get.html). On the legacy full-import working-copy path, changed values block as possible external edits. Unchanged/null metadata is not complete component drift control: that path requires a single editor. The 26.2 partial path checks fresh server content as described below. DB operations are incompatible with active working-copy plans; explicit invalidate returns to the full path. Production and new applications keep that path.

A confirmed import with failed verification is `verification_failed`, retaining the old successful checkpoint. A lost response, interrupted write or local persistence failure after mutation is blocked as `outcome_unknown`; leftover `importing` also requires reconciliation. Invalidate never removes unknown ownership. Explicit status reconciliation may export for diagnosis and never grants retry permission. Baseline restore uses the existing separate backup-bound plan, fresh safeguards and exact approval; old sync becomes invalidated before the restore write starts. Restoring each intermediate import is outside this version. Interrupted local source installation also leaves a blocked durable record for inspection rather than advertising a partially installed ready copy.

The full-export behavior described below continues for projects without active sync and for separate restore plans. Legacy local [measurements](evidence/working-copy-local.json) establish export counts and filesystem behavior with fixture Oracle methods only; those measurements do not establish connected imports, browser acceptance or restore. See [implementation status](implementation-status.md) for current 26.2 evidence and limitations.

## APEX 26.2 partial imports

Partial import is implemented in this source checkout and is not included in the published npm `1.3.0` package. It applies to an existing development/test application with a trusted sync checkpoint, Oracle-exported 26.2 sources and a compatible target. The capability gate checks actual `apex import -files` support and the reviewed SQLcl `26.3.0.260.1620` / MMD `26.2.0+3479` tuple. It requires direct SQLcl CLI transport inside the runtime; both `apexrest_ship` over MCP and the CLI can use it. SQLcl's own MCP mode and ORDS transport retain their full-import/restriction behavior.

`apexrest_ship` and `deploy plan` accept `importMode` / `--import-mode`:

| Mode | Planned scope |
| --- | --- |
| `auto` (default) | Eligible local changes become a file import; otherwise the preview explains why a full plan is needed. |
| `files` | Only the explicit, nonempty application-relative `files` / `--files` selection is eligible. No dependency additions or full fallback. |
| `full` | Complete application import with the established full-import safeguards. |

File selection compares the trusted baseline, local inventory and a fresh server export. Unequal local/server edits to the same file block with `IMPORT_CONFLICT`, including conflicts outside an explicit selection. Remote-only edits are preserved in the effective application. The whole effective tree is compiled before planning, so a page depending on a new local LOV requires the LOV in the selected set if it is absent on the server. The preview's `importSelection.dependencies` lists selected shared-component files; it does not discover or add missing dependencies.

Full-import reasons include `trusted-sync-baseline-required`, `existing-application-required`, `production-requires-full-import`, `database-operations-require-full-import`, `deleted-files-require-full-import`, `unsupported-component-files` and `no-changed-files`, plus capability failures. These reasons do not waive existing restrictions: active sync still blocks database operations, production still requires protected approval, and incompatible target versions block planning. Observed remote changes block an automatic full fallback with `SYNC_SERVER_CHANGED` until reconciled. `files` reports `PARTIAL_IMPORT_UNSUPPORTED` for an ineligible request and never widens its scope. Themes, templates, plug-ins, workspace components, static files/assets and authentication/authorization files are excluded from partial import.

Schema v4 partial plans bind the exact file list, trusted checkpoint, fresh server snapshot, validated effective tree, source/configuration/toolchain hashes and target. Apply rechecks that binding and current content, creates a fresh full SQL backup, freezes the effective tree and executes one SQLcl `apex import -files` command. A granular `deploy apply --plan ...` executes the saved selection; `ship` in apply mode creates a fresh plan from the supplied mode and paths.

After import, a full APEXlang export must match the expected effective application under the plan's readback policy. Unselected files stay byte-exact; narrowly accepted selected-file normalizations and both hashes are recorded in `readback-verification.json`. Only after verification and established required suites succeed does the actual server export become the checkpoint. Remote-only edits are reconciled locally and unselected local work remains dirty; concurrent local changes are retained and require reconciliation. Confirmed import with failed readback or local reconciliation is a verification failure; an unconfirmed write is `outcome_unknown`. Neither result authorizes retry or automatic rollback. Durable before/effective/server snapshots, run journals and full SQL backups remain available for investigation. See the [26.2 guide](apex-26.2.md#backup-verification-and-recovery) for the exact readback policy.

## Ship: plan, grant, apply, verify

`apexrest_ship` (CLI `apexrest ship --env NAME --mode plan|apply --import-mode auto|files|full --user-request TEXT`) is the agent's deployment entry point. `mode:plan` validates with the Oracle compiler, reads the target and writes `.apexrest/plans/ship-<id>.json` plus private staging/snapshot evidence; it does not mutate the Oracle application. Review `importSelection.requestedMode`, `resolvedMode`, `files`, `dependencies` and `reasons`, plus the target and risks. The preview caps file/dependency lists at 50; inspect the saved plan when truncated. `mode:apply` plans again in-process, refuses production targets and plans with unreviewed risks before any grant is written, then hands the apply phase to a detached worker that records a deploy grant from `userRequest` (the user's literal instruction) bound to the canonical project root, target digest and plan digest, deploy only, expiring with the plan and marked `grantedBy: "ship"`; backs up, migrates when the full plan includes database operations, imports, verifies and runs the required suites (job phases `backing_up`, `migrating`, `importing`, `verifying`, `testing`); and removes the grant whether the attempt succeeded or failed (`grant.removed` reports a removal failure). The granular `deploy plan` / `deploy apply` commands below implement the same checks and remain the path for production, restore plans and CI.

The 2026-09-12 user amendment treats an explicit create/update/import request for an identified development/test application as authorization for the necessary scoped import. After reviewing the concrete plan, the runtime records the existing instruction as that short-lived local deploy grant bound to the exact project, target and plan; preserves unrelated policy, retains the authorization record, and removes the grant after the attempt. The agent does not ask the same permission twice or stop at a plan. Every local deploy grant must carry `planDigest` equal to the reviewed plan digest and an `expiresAt` no later than the plan's `expiresAt`; otherwise apply is blocked with `DEPLOY_APPROVAL_REQUIRED`. This records consent already given and does not invent consent, authorize unrelated database writes, or replace protected production signatures. Identity, SQL backup, drift, coordination, source freezing and unknown-outcome handling remain mandatory.

Application-only verification may use an explicitly authorized isolated profile with compiler, real read-only SQL reconciliation and in-app browser observations, while retaining the original required-suite profile and its historical results. No configured automated suites means none ran, not that SQL/E2E passed. See [application-only changes](testing.md#application-only-changes) and the [browser verification rule](testing.md#browser-verification).

Deploy works on a clean supported APEX installation without APEXREST service tables. Coordination is always local: immutable migration history and schema ownership are stored under `$APEXREST_HOME/deployment-control/`, and no control-table query or DDL ever occurs. There is no database-backed coordination mode. Separate read and deploy connection references allow least privilege.

`deploy plan --env dev --import-mode full --out plans/dev.json` explicitly plans a complete application import. It reads exact database unique name, service, schema, workspace and application identity, exports target content on the full-export path, hashes sources/configuration/toolchain and validates with the real compiler. Validation passes only when the compiler output contains a success marker and no error indication, including counted summaries such as `3 errors`; otherwise it is `VALIDATION_UNCONFIRMED`. Plans expire after 30 minutes, and apply rejects a plan whose lifetime exceeds that limit as `PLAN_TAMPERED`. Planning exports to local staging but never imports to the DB. Full application imports include pages and shared components, even when only one page changed. Eligible 26.2 `auto`/`files` plans use the partial path above; 26.1 retains full-import behavior. Unsupported components must be blocked by the real compiler; coverage is not universal.

`deploy apply --plan plans/dev.json` revalidates the plan and external policy, current target and compiler. The live target and migration history must equal the copies stored in the plan; a difference is `PLAN_TAMPERED`. Authentication and authorization risk is recomputed from a live export rather than trusted from the plan: changed authentication/authorization files and content-level APEXlang changes such as `authentication`, `authorizationScheme` or authentication/authorization blocks are `PLAN_TAMPERED` when the plan omits them. A copied, checksummed SQL export is taken whenever the live application exists, regardless of the plan's `backupRequired` value, before any application or schema writes. Backup files are owner-only (`0600`), and Oracle export staging is removed after use. After a second drift check, sources are frozen and checksummed. Ordered immutable migrations persist a `started` record in the local history before executing; changed checksums or unresolved outcomes block future plans. Package scripts execute after migrations. SQLcl's first error stops execution; DDL is not assumed transactional.

Local coordination serializes runners sharing one managed home for the same DB/service/parsing schema, including different apps in that schema. A confirmed dead same-host owner can be reclaimed only while preparing. Writing ownership is retained after an unknown outcome and never automatically reclaimed after a crash. The plan binds its coordination scope and local store identity. Preserve the deployment-control directory: a new machine or deleted history cannot infer previously applied migrations from Oracle. Independent machines or homes are not coordinated by the plugin: use one durable deployment runner/home and serialize multiple machines externally (for example one CI deploy job). Local filesystem locks are not a distributed database guarantee. Lock files and atomic state writes are published only after their content and directory entry are flushed. A lock file without a readable owner that is older than 30 seconds reports `LOCK_CORRUPT`: confirm that no apexrest operation is running on any host, then delete the named lock file and retry. There is no automated recovery command for this case.

The earlier optional table-backed mode (`apexrest_deploy_locks`/`apexrest_migrations` with a row lease and heartbeat) has been removed; its concurrent-Oracle behaviour was never verified. A target that previously used it keeps those tables untouched; reconcile their migration history into the local store before the first local plan.

The app is imported with explicit workspace/schema/ID, identity verified and required suites executed. Any empty/skipped/blocked required suite fails the gate. After a confirmed import, an unexpected verification error is `POST_DEPLOY_VERIFICATION_FAILED`, not an unknown import outcome. On cancellation, timeout or lost lease after write, the result is `outcome_unknown`; no automatic reapply occurs. `deploy status --run UUID` reads target/export/history for reconciliation and never turns uncertainty into success.

utPLSQL is a dependency only when a SQL test suite is selected/required. Application-only projects can deploy without it; do not remove genuinely required test suites to make an existing gate green. Clean APEX support changes control storage, not authorization or quality requirements. Plans created before the coordination field was introduced must be regenerated.

`deploy restore-plan --backup UUID --out plans/restore.json` verifies the backup and current target, creates a new plan, and requires a grant for that exact digest. Apply creates a new backup, then restores one complete non-split `f<ID>.sql` Oracle export with explicit install target. Split/unknown layouts are blocked. When the application was absent at plan time, post-restore identity verification uses the alias recorded with the backup, so a successful restore is not reported as `outcome_unknown`. This restores APEX metadata only; business data and destructive schema changes require separate DBA recovery. General destructive/privileged/authentication changes stay blocked pending an explicit recovery workflow.

## Migrations and SQL client commands

Migrations must sit directly in `database.migrationsDir` and use ordered names such as `0001__customers.sql`. Planning rejects subdirectories (`INVALID_MIGRATION_LAYOUT`), other names (`INVALID_MIGRATION_NAME`) and two files with one numeric version (`DUPLICATE_MIGRATION_VERSION`). A new migration with a version lower than the highest applied version is `MIGRATION_OUT_OF_ORDER`. Migrations run in numeric version order, then package scripts by path.

Migration and package scripts may contain SQL and PL/SQL only. A line that SQLcl or SQL*Plus could interpret as a client command, for example `host`, `!`, `$`, `@`, `@@`, `start`, `spool`, `connect` or an accepted abbreviation, adds the `sqlcl-script-control` risk. Like other risks without a reviewed recovery workflow, it blocks authorization with `RECOVERY_REVIEW_REQUIRED`. The scanner deliberately over-reports, including lines inside comments and strings. SQL test files are checked the same way (see [testing](testing.md)). In CLI mode, SQLcl sessions for migration and package scripts, `apex import`, metadata restore and SQL test scripts start with restriction level `-R 2`, which blocks host commands and file writes such as `spool` while still allowing `@file`.

## Production approval

A target is production when its environment in `apexrest.json` has `kind: "production"` or when its `targetDigest` is listed in `productionTargets` of `$APEXREST_HOME/production-trust.json`. A listed target is production regardless of project configuration: local deploy grants, working-copy sync and remote tests are refused for it.

Production apply requires `CI=true`, `APEXREST_APPROVAL_FILE` and `APEXREST_APPROVAL_PUBLIC_KEY_FILE` on a protected POSIX runner, plus an administrator-owned trust file:

```json
{
  "schemaVersion": 1,
  "approvalKeys": [{ "sha256": "SPKI_DER_SHA256_OF_APPROVAL_PUBLIC_KEY", "reviewer": "release-approver" }],
  "productionTargets": ["TARGET_DIGEST_FROM_REVIEWED_PLAN"]
}
```

APEXREST never writes this file. It must be a regular file rather than a symbolic link, owned by another account such as root, not writable by the running process and not group- or world-writable (`PRODUCTION_TRUST_UNPROTECTED`). A missing file is `PRODUCTION_TRUST_REQUIRED`; unreadable or invalid content is `PRODUCTION_TRUST_INVALID`. Running as the file owner, including root when root owns it, is refused. Windows is refused with `PRODUCTION_TRUST_UNSUPPORTED` because ACLs are not inspected. The environment variable only selects a public key: the SHA-256 of that key in SPKI DER form must be listed in `approvalKeys` (`APPROVAL_KEY_UNTRUSTED`), and an optional `reviewer` there must match the attestation.

The external Ed25519 attestation contains `planDigest`, `planId`, `projectId`, `targetDigest`, `expiresAt`, `reviewer` and `signature`. The signature covers the canonical JSON of all other fields. Each value must match the plan and project, and the attestation must not have expired; otherwise apply fails with `APPROVAL_INVALID`. Attestations without `planId` and `projectId` are rejected by the strict schema, as is `approved=true`. The repository cannot supply or modify the runner's verification key or trust file. No agent-facing operation signs approvals. If the runner user can delete `production-trust.json`, it can also remove the trust-file production classification; production approval itself still fails closed without the file.

# Запуск APEXREST у Codex Cloud

[English](codex-cloud.md) | Українська

Запускайте комплектний **CLI APEXREST усередині контейнера Cloud**, використовуючи ORDS через HTTPS для доступу до бази. Наведений приклад перетворює налаштування окремого Cloud-проєкту на скрипти для повторного використання. Він не реєструє desktop-плагін, не надає його MCP-інструменти хмарному агенту й не запускає desktop-панель розробки. Ці інтеграції потребують окремої перевірки хоста; див. [аудит інтеграції Codex](codex-integration.uk.md).

## 1. Підготуйте репозиторій застосунку

Скопіюйте файли з [каталогу прикладу Cloud](examples/codex-cloud/) до `scripts/codex-cloud/` у репозиторії застосунку, підключеному до Codex Cloud. Зберігайте всі файли разом. Із репозиторію застосунку, маючи локальну копію APEXREST:

```sh
mkdir -p scripts/codex-cloud
cp /path/to/apexrest-codex/docs/examples/codex-cloud/* scripts/codex-cloud/
```

До запуску setup додайте ці записи до `.gitignore` застосунку:

```gitignore
.codex/cloud/
.apexrest/
```

Закомітьте скрипти прикладу та правила ігнорування в типову гілку репозиторію, з якої готується кеш Cloud, і переконайтеся, що вони також є в гілці задачі. При відновленні кешу Cloud переходить на гілку задачі; див. [кешування контейнерів](https://learn.chatgpt.com/docs/environments/cloud-environment). Створені інструменти, облікові дані, журнали, плани й резервні копії мають залишатися приватними. Скрипти є прикладами документації; плагін чи його npm-пакет не встановлює їх автоматично.

[Файл версії](examples/codex-cloud/version.sh) закріплює готову збірку за Git-комітом `d8405d935d621d021523d4a17d9dd3d5e959fcb5` із версією маніфесту `0.2.0-beta.1+codex.20260919143707`. Setup перевіряє обидва значення й використовує `plugins/apexrest-apex/runtime/apexrest.mjs`; npm-випуск або збирання TypeScript не потрібні. Для переходу на новішу збірку перевіряйте та змінюйте обидва значення разом.

## 2. Налаштуйте середовище Cloud

Виберіть репозиторій застосунку в налаштуваннях середовища Codex Cloud. У версіях пакетів виберіть **Node.js 24** та **Java 21**. Java має бути **JDK із `jdk.compiler`**, а не лише JRE. Також потрібні Git і Bash.

Задайте наведені змінні середовища. Замініть усі приклади цілі значеннями вашого середовища розробки чи тестування:

| Змінна                           | Значення або призначення                                                                                    |
| -------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `CODEX_CLOUD`                    | `1`; явне ввімкнення Linux-налаштування цього прикладу.                                                     |
| `APEXREST_ACCEPT_ORACLE_LICENSE` | `1` лише після прийняття [умов Oracle](https://www.oracle.com/downloads/licenses/oracle-free-license.html). |
| `APEXREST_PERSIST_CREDENTIALS`   | `1` лише якщо ви дозволяєте описане нижче збереження облікових даних.                                       |
| `APEXREST_ORDS_URL`              | URL схеми, наприклад `https://ords.example.invalid/ords/app_user/`.                                         |
| `APEXREST_ORDS_USERNAME`         | Ім’я користувача бази, наприклад `app_user`; псевдонім схеми може відрізнятися.                             |
| `APEXREST_CONNECTION_REF`        | Локальна назва з’єднання, наприклад `cloud-dev` (типове значення).                                          |
| `APEXREST_EXPECTED_SCHEMA`       | Необов’язкова точна очікувана схема парсингу з перевірки ідентичності.                                      |
| `APEXREST_EXPECTED_SERVICE`      | Необов’язкова точна очікувана служба бази з перевірки ідентичності.                                         |

Додайте **`APEXREST_ORDS_PASSWORD` як Secret**, а не звичайну змінну середовища чи файл репозиторію. Обліковий запис уже повинен мати дозволений доступ до REST-Enabled SQL цієї схеми ORDS. Використовуйте URL схеми, а не URL APEX-застосунку чи endpoint `/_/sql`; див. [налаштування ORDS](ords.uk.md).

Секрети Cloud доступні під час setup, після чого видаляються із середовища агента. Цей приклад навмисно зберігає файл облікових даних для подальших команд CLI. Кеш контейнера може зберегти цей файл, а кеші Business/Enterprise можуть бути спільними для користувачів середовища. Використовуйте середовище, користувачам якого дозволено доступ до цього облікового запису бази. Див. [документацію OpenAI про хмарні середовища](https://learn.chatgpt.com/docs/environments/cloud-environment).

За `APEXREST_PERSIST_CREDENTIALS=1` setup передає секрет через тимчасовий файл, доступний лише власнику, до `connection add --password-file`, видаляє тимчасовий файл і залишає облікові дані APEXREST у `.codex/cloud/tools/credentials/` з POSIX-правами `0600`. Це **не зашифроване сховище**: агент і процеси того самого користувача можуть прочитати файл. Якщо таке збереження неприйнятне, не вмикайте прапорець і не використовуйте цей приклад із підключенням. Не виводьте секрет, не вмикайте трасування shell і не додавайте `.codex/cloud/` до комітів чи спільних артефактів.

## 3. Задайте команди setup і maintenance

**Setup script:**

```sh
bash scripts/codex-cloud/setup.sh
```

**Maintenance script:**

```sh
bash scripts/codex-cloud/setup.sh --maintenance
```

Setup перевіряє закріплену копію коду, показує план і встановлює керовані залежності з `--skip-browser`, готує приватний JDK, обирає `sqlcl configure --mode cli --database-transport ords`, зберігає з’єднання та виконує `doctor` і перевірку ідентичності бази лише читанням. Він не створює застосунок чи бізнес-дані й не надає дозволу на розгортання.

Maintenance використовує встановлену збірку та облікові дані, оновлює Java proxy/CA й повторює перевірку з’єднання. Залежності не перевстановлюються. Якщо збірка відсутня, закріплена версія змінилася чи бракує облікових даних, повторіть setup із доступним секретом. Для ротації пароля оновіть Secret і повторіть setup; збереження старих локальних облікових даних не є ротацією.

Засіб запуску відновлює `APEXREST_HOME`, `APEXREST_JAVA_HOME` та вибраний Node під час кожного виклику. Самого `export` у setup недостатньо для фази агента. Cloud може відновити контейнер із кешу та запустити maintenance; після несумісних змін setup використовуйте **Reset cache**. Див. [життєвий цикл середовища](https://learn.chatgpt.com/docs/environments/cloud-environment).

## 4. Налаштуйте мережевий доступ

Увімкніть агенту інтернет-доступ до точного хоста ORDS і дозвольте **POST**, потрібний REST-Enabled SQL навіть для запитів лише читанням. Доступ для завантажень під час setup і доступ фази агента налаштовуються окремо. Див. [документацію OpenAI про інтернет-доступ агента](https://learn.chatgpt.com/docs/cloud/internet-access).

Приклад використовує HTTPS: наявність HTTP proxy у Cloud не підтверджує доступності Oracle listener на порту 1521; звичайні URL ORDS з `http:` приймаються лише для loopback. Доступ до listener не припускається. Setup також потребує доступу до канонічного GitHub-репозиторію та хостів завантаження залежностей, показаних у плані інсталятора.

[Мережевий скрипт](examples/codex-cloud/network.sh) вмикає `NODE_USE_ENV_PROXY=1`. Тоді завантаження постачальників враховують `HTTPS_PROXY` і `NO_PROXY`; якщо proxy налаштовано, але поточний Node не може його застосувати, setup зупиняється з `PROXY_UNSUPPORTED` замість обходу proxy. [Java-скрипт](examples/codex-cloud/setup-java.mjs) копіює JDK середовища до `.codex/cloud/java`, записує proxy в його приватний `conf/net.properties` та імпортує сертифікати середовища з `NODE_EXTRA_CA_CERTS` до приватного `lib/security/jssecacerts`. Типові кореневі сертифікати зберігаються, JDK хоста не змінюється. APEXREST очищає змінні параметрів Java для дочірніх Oracle-процесів, тому одного `JAVA_TOOL_OPTIONS` тут недостатньо.

Скрипт підтримує HTTP proxy без облікових даних у URL та читає `https_proxy`, `HTTPS_PROXY`, `http_proxy`, потім `HTTP_PROXY`. Записи хостів/доменів у `NO_PROXY` переносяться до Java; CIDR-записи залишаються через proxy. Непідтримувані налаштування proxy спричиняють явну помилку. Залишайте перевірку TLS-сертифікатів увімкненою; оновлюйте приватне сховище довіри при зміні CA середовища.

## 5. Перевірте запуск із хмарної задачі

Після успішного setup почніть задачу й виконайте ці команди з репозиторію застосунку. Замініть `cloud-dev`, якщо вибрали іншу назву з’єднання:

```sh
bash scripts/codex-cloud/apexrest doctor --json
bash scripts/codex-cloud/apexrest sqlcl status --json
bash scripts/codex-cloud/apexrest connection list --json
bash scripts/codex-cloud/apexrest connection test --name cloud-dev --json
bash scripts/codex-cloud/apexrest --help
```

Перевіряйте фактичний JSON і коди завершення: режим має бути `cli`, мережевий транспорт — `ords`, а ідентичність з’єднання повинна відповідати потрібній базі/схемі. Успішної команди `doctor` недостатньо: вона звітує про окремі перевірки інструментів і не тестує базу. Її поля `nativeHost: requires-host-verification` та `database: not-configured` не скасовують окремо успішної перевірки з’єднання. Відсутність локального виконуваного Codex також сама собою не перешкоджає прямим операціям CLI/ORDS.

Назва з’єднання належить APEXREST, а не сховищу збережених з’єднань SQLcl; не замінюйте команду на `sql -name cloud-dev` або `connection test --saved`. Зберігайте лише очищені докази; результат перевірки ідентичності може містити приватні назви цілі.

## 6. Додайте інструкції проєкту для агента

Додайте короткий розділ для Cloud до `AGENTS.md` репозиторію застосунку:

```markdown
## APEXREST in Codex Cloud

- Run APEXREST commands with `bash scripts/codex-cloud/apexrest`.
- Check doctor, SQLcl configuration and the configured connection identity first.
- Use SQLcl CLI with ORDS; this bootstrap does not register native plugin tools.
- Keep `.codex/cloud/` and `.apexrest/` private. Never print credentials.
- Do not run setup, native plugin registration or dependency downloads in every task.
- Use the configured project/environment and existing deployment safeguards.
- Report compiler checks, database checks and browser observations separately.
```

Перед роботою із застосунком налаштуйте ціль в `apexrest.json`: workspace, схему, ID застосунку, ідентичність бази та відповідні назви з’єднань для читання/розгортання. Перевірте довіру до проєкту й збережіть валідацію, резервну копію, дозвіл для точного плану, захист від змін цілі та невідомого результату з [конфігурації](configuration.uk.md) й [безпеки розгортання](deployment-safety.uk.md). Встановлення та успішна перевірка з’єднання не надають дозволу на імпорт.

Приклад зберігає локальну історію розгортання в `APEXREST_HOME`. Кеш Cloud не є надійним сховищем резервних копій або координацією між контейнерами: зберігайте приватні копії/історію поза тимчасовим контейнером і впорядковуйте запуски перед дозволом на розгортання. Не видаляйте через reset записи нез’ясованої операції й не починайте непомітно нову історію для тієї самої схеми.

Браузерні залежності пропущені. Браузерні перевірки потребують окремо налаштованих інструментів, автентифікації та фактичних спостережень. Цей CLI-bootstrap не підтверджує роботу `$apexrest-work`, вбудованої панелі чи автоматичного виявлення навичок/MCP у Cloud. Для описаного процесу використовуйте засіб запуску й явно повідомляйте про недоступні перевірки.

## Усунення несправностей

| Симптом                                                             | Дія                                                                                                                |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Setup завершується з “Skipping Cloud setup”                         | Задайте `CODEX_CLOUD=1` у налаштуваннях середовища.                                                                |
| Непідтримуваний Node або немає компілятора JDK                      | Виберіть Node 24 та JDK 21, потім повторіть setup.                                                                 |
| Після відновлення бракує закріпленої збірки/runtime/облікових даних | Повторіть setup із Secret; maintenance не відновлює середовище без кешу.                                           |
| HTTP 401/403 або невдала перевірка ідентичності                     | Перевірте обліковий запис, доступ до REST-Enabled SQL, URL схеми, очікувану ідентичність і дозвіл POST для агента. |
| Тайм-аут Java або помилка сертифіката                               | Перевірте proxy/CA й виконайте maintenance; не вимикайте TLS.                                                      |
| CLI працює, але інструментів плагіна чи панелі немає                | Приклад не встановлює й не перевіряє нативну інтеграцію Cloud; продовжуйте через CLI.                              |

## Межі перевірки

Посібник та узагальнені скрипти перевірено локально; для цієї зміни документації не виконували фактичний setup/відновлення Codex Cloud, виявлення нативного плагіна, операцію з підключенням до Oracle чи браузерну сесію. Наявні [докази ORDS](ords.uk.md#передумови-й-перевірка) зберігають початкову ціль та обсяг виконання. Після наведених перевірок зафіксуйте нові докази Cloud; див. [стан реалізації](implementation-status.uk.md) та [наступні дії](next-actions.uk.md).

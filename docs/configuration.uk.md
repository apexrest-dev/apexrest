# Конфігурація та з’єднання

[English](configuration.md) | Українська

Оберіть браузер перевірки (`codex` або `external`) у [налаштуваннях панелі](panel.uk.md). Реалізація використовує поточну сесію Codex та її дозволи.

Проєкт має один `apexrest.json` та один зафіксований toolchain lock. `project init` створює обидва файли з порожньою мапою середовищ. Кожна операція з ціллю потребує явного середовища; плагін ніколи не вгадує базу даних, робочий простір чи ID застосунку.

## Налаштування середовища

Додайте запис на зразок `environments.dev` у створений `apexrest.json`:

```json
{
  "kind": "development",
  "readConnectionRef": "dev-read",
  "deployConnectionRef": "dev-deploy",
  "workspace": "YOUR_WORKSPACE",
  "parsingSchema": "YOUR_SCHEMA",
  "applicationId": 123,
  "baseUrl": "https://your-host.example/ords/r/workspace/crm/",
  "databaseIdentity": {
    "dbUniqueName": "YOUR_DB",
    "serviceName": "YOUR_SERVICE"
  },
  "allowedOrigins": ["https://your-host.example"],
  "expectedMarker": "apexrest-crm",
  "deploymentControl": "local"
}
```

Це заповнювачі, а не робоча ціль. Використайте справжні унікальну назву бази даних і сервіс, робочий простір, parsing schema та ID застосунку. `expectedMarker` має відповідати специфічному DOM-маркеру застосунку, якщо цього потребують тести. `allowedOrigins` має містити origins, потрібні браузерним/API тестам, включно зі схваленими перенаправленнями SSO або CDN. Додавання origin не дозволяє змінювати його дані.

Згенерований `schemas/project.schema.json` є точною публічною схемою. Невідомі поля відхиляються. Шляхи коду, тестів, міграцій, пакетів, артефактів та інструментарію мають залишатися всередині проєкту.

## Список і перевірка збережених з’єднань SQLcl

Для перевірки доступу до бази проєкт і псевдонім APEXREST не потрібні. Відкрийте **List saved SQLcl connections** або **Test saved SQLcl connection** у [TUI](tui.uk.md), виберіть збережену назву й натисніть Enter. Введення фільтрує список, Ctrl+R оновлює його.

```sh
apexrest connection list --saved --json
apexrest connection test 'Development connection' --saved --json
```

Команди читають сховище SQLcl безпосередньо й перевіряють точну назву з’єднання запитом ідентичності лише для читання. Якщо сховище порожнє або бракує облікових даних, налаштуйте їх у SQLcl. Далі можна зареєструвати посилання для середовища проєкту, як описано нижче. CLI без `--saved` використовує саме ці посилання.

Для HTTP-доступу без доступного listener налаштуйте URL, користувача й пароль ORDS на рівні плагіна та виберіть мережевий транспорт. Див. [SQL через ORDS](ords.uk.md). Наведені нижче збережені з’єднання SQLcl стосуються прямого доступу.

## Збереження посилань на з’єднання

Інтерактивно створіть іменовані з’єднання в локальному сховищі SQLcl. Потім зареєструйте їхні назви:

```sh
apexrest connection add dev-read --sqlcl-name saved-read-connection
apexrest connection add dev-deploy --sqlcl-name saved-deploy-connection
apexrest connection test dev-read --json
```

Приклади передбачають [керований засіб запуску CLI](getting-started.uk.md#використання-cli). APEXREST зберігає назви з’єднань, а не паролі. З’єднання для читання може мати менше привілеїв, ніж з’єднання розгортання. Видалення посилання APEXREST через `connection remove` зберігає запис сховища SQLcl. Ніколи не записуйте облікові дані в `apexrest.json`, приклади середовища, запити чи повідомлення про помилки.

## Довіра та дозвіл для проєкту

Приватна політика розташована в `$APEXREST_HOME/policy.json`, типово — `~/.apexrest/policy.json`. Перегляньте виконуваний код проєкту перед додаванням його канонічного шляху до `trustedProjects`:

```json
{
  "schemaVersion": 1,
  "trustedProjects": ["/canonical/reviewed/project"],
  "grants": []
}
```

Зберігайте цю політику поза репозиторієм. Дозвіл прив’язує `projectRoot`, точний `targetDigest` плану, строк дії та дозволені операції `deploy` або `test`. Deploy grant, зокрема для відновлення, має також містити `planDigest`, що дорівнює digest точного плану, і `expiresAt` не пізніше за строк дії плану; інакше apply блокується з `DEPLOY_APPROVAL_REQUIRED`. Схема політики досі приймає grant без `planDigest`, але такий grant ніколи не дозволяє розгортання. Test grant прив’язує проєкт, ціль, операцію та строк дії.

Для явного запиту створити, оновити чи імпортувати визначений застосунок розробки/тестування Codex може записати вже наданий дозвіл як короткостроковий grant із точним поточним `planDigest`, лише `deploy` та строком дії не довшим за план. Він зберігає приватний запис дозволу, не змінює сторонні grants і видаляє grant задачі після спроби. Файл проєкту чи відповідь інструмента не можуть надавати таку згоду. Інші цілі, зміни бізнес-таблиць, автентифікації та захищені production-операції потребують відповідного обсягу дозволу.

Для production потрібні процес зовнішнього підпису та файл `$APEXREST_HOME/production-trust.json`, що належить адміністратору, з [безпеки розгортання](deployment-safety.uk.md#схвалення-production); доступна для запису локальна політика не замінює захищений runner. Ціль, указана в `productionTargets` цього файлу, є production, навіть якщо її середовище в `apexrest.json` має інший `kind`.

## Вибір координації розгортання

| Режим                 | Сховище й межі                                           | Експлуатаційна вимога                                                                        |
| --------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `local` або не задано | Стійка історія та володіння схемою в керованому home     | Зберігайте home; незалежні машини виконуйте послідовно зовнішніми засобами                   |
| `database`            | Явно вибрані службові таблиці й оренда блокування в базі | Встановлюйте перевірені таблиці лише з дозволом; звіряйте наявну історію перед зміною режиму |

Локальний режим є типовим і не потребує службових таблиць APEXREST. План прив’язує вибраний backend та ідентичність сховища. Видалення локальної історії чи непомітний перехід до нового home не є процедурою відновлення. Вибраний database backend ніколи непомітно не переходить до локального сховища.

## Вибір обсягу тестів

`tests.requiredSuites` визначає набори, які мають пройти. `tests.mutationAllowedEnvironments` перелічує явно налаштовані середовища, де віддаленим тестам дозволено змінювати дані. Production-тести заборонені, зокрема для цілей, класифікованих як production у `production-trust.json`. Порожній, пропущений чи заблокований обов’язковий набір провалює перевірку якості.

Порожній застосунок або явно дозволений ізольований профіль лише застосунку може не мати автоматизованих наборів. Тоді повідомте, що вони не запускалися, а фактичні результати компілятора, вихідних запитів і вбудованого браузера запишіть окремо. Не прибирайте обов’язкових CRM чи наявних інтеграційних наборів лише заради успішної перевірки. Див. [тестування](testing.uk.md).

## Конфігурація середовища виконання

| Змінна                | Призначення                                                           |
| --------------------- | --------------------------------------------------------------------- |
| `APEXREST_HOME`       | Приватне кероване середовище, політика, з’єднання та стан розгортання |
| `APEXREST_SQLCL`      | Явно вибраний перевірений виконуваний файл SQLcl                      |
| `APEXREST_JAVA_HOME`  | Java для SQLcl                                                        |
| `APEXREST_RESOURCES`  | Перевизначення зібраних ресурсів довіреним хостом                     |
| `NODE_EXTRA_CA_CERTS` | Додаткові центри сертифікації для з’єднань Node                       |

Ці перевизначення належать довіреному локальному хосту, а не входам під контролем проєкту. Bootstrap підтримує проксі середовища Node 24 через `--use-env-proxy`. Завантаження постачальників враховують `HTTPS_PROXY`/`HTTP_PROXY` і `NO_PROXY` через підтримку проксі середовища в Node; якщо проксі налаштовано, але цей Node не може його застосувати, setup завершується з `PROXY_UNSUPPORTED` замість обходу проксі. Шляхи з пробілами й Unicode підтримуються; лапки, підстановки та керівні символи в токенах SQLcl відхиляються.

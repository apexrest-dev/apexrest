# Каталог компонентів

[English](component-catalog.md) | Українська

Знайдіть компонент, перегляньте його параметри й адаптуйте рецепт APEXlang до свого застосунку. Каталог постачається з APEXREST починаючи з 1.1.0 і працює офлайн, без проєкту чи підключення до довідкового додатка. Він охоплює Universal Theme 26.1 Reference, включно з різними способами розміщення та прикладами; це не твердження про покриття всіх можливостей Oracle APEX.

Список компонентів і приклади можна переглянути в [Universal Theme Reference](https://apex.oracle.com/ut).

## Пошук і читання

```sh
apexrest docs search --corpus components --query "metric card" --kind template --version 26.1 --limit 3 --json
apexrest docs read --id component:catalog --json
```

Відповідний MCP-пошук використовує `apexrest_reference_search`:

```json
{
  "corpus": "components",
  "query": "картка показника",
  "kind": "template",
  "version": "26.1",
  "limit": 3
}
```

Прочитайте отриманий ID через `apexrest_reference_read`; використовуйте `nextOffset` для продовження документа та `nextResultOffset` для наступних результатів. Параметри й рецепти зберігаються окремо, тому один запит не завантажує цілу сім’ю компонентів. Англійські й українські пошукові назви ведуть до тих самих версійних записів. Наявний пошук за замовчуванням використовує `corpus: "apexlang"`; значення чинних Oracle IDs зберігається.

## Використання рецепта

Спочатку перевірте джерела, тему та MMD поточного проєкту. Оберіть правильний спосіб розміщення: шаблон списку Media List і template component Media List мають різні контракти, як і класичний звіт Comments та template component Comments. Прочитайте рецепт, його параметри й потрібні Oracle-контракти.

Узгоджено адаптуйте імена сторінок і полів, DOM IDs, SQL-проєкції, ключі, спільні посилання та AJAX submitted items. Синтетичні приклади показують потрібну структуру даних; вони не підключають ваші бізнес-дані. Редаговані елементи потребують описаного контракту таблиці або API. Скомпілюйте весь адаптований застосунок перед чинним процесом дозволеного розгортання.

Рецепт зі статусом `ready` має повний набір локальних залежностей і доказ справжньої офлайн-компіляції для заявленого scaffold та MMD. Виконання SQL, імпорт і браузерна перевірка мають окремі поля. `not-run` не означає успіху. Непідтриманий приклад залишається доступним із конкретною причиною. Наявність template option у довідковому додатку сама по собі не підтверджує компіляцію довільної композиції APEXlang.

## Джерела та сумісність

Початкове джерело — Universal Theme 26.1 Reference: APEX 26.1.4, Universal Theme 26.1, SQLcl 26.1.2 і MMD 26.1.0+3102. Інвентар містить 122 сторінки, 987 регіонів, 539 template options і 164 атрибути компонентів Universal Theme. Документаційні та службові регіони класифіковано; не кожен із них є готовим рецептом.

Каталог поєднує знімок застосунку, дозволені метадані APEX, відповідні метадані компілятора та зафіксовані Oracle APEXlang-довідники. Параметри зберігають повний контекст, відповідності значень, defaults, умови й походження. Опції оболонки регіону відокремлено від опцій вкладеного шаблону. Поточні значення, defaults і presets розрізняються; `#DEFAULT#` — маркер, а не CSS-клас.

Ревізії каталогу прив’язані до hashes джерел і вмісту. Manifest окремо фіксує APEX, тему та MMD. Оберіть відповідну версію й перевірте сумісність перед адаптацією рецепта. Каталог не підміняє цільову збірку непомітно.

## Оновлення та розповсюдження

Отримання джерел — окрема операція розробника з явно заданими saved SQLcl connection, application, workspace і schema. Вона перевіряє ідентичність цілі перед експортом або читанням метаданих. Операція створює приватні локальні дослідницькі файли; не імпортує застосунок і не змінює бізнес-таблиці. Звичайний пошук у каталозі не оновлює знімок БД.

Задайте `REFERENCE_CONNECTION`, `REFERENCE_APPLICATION_ID` (числовий ID), `REFERENCE_WORKSPACE` і `REFERENCE_SCHEMA` для дозволеного джерела лише для читання. Створіть новий приватний знімок поза репозиторієм, перевірте його та нормалізуйте:

```sh
node scripts/capture-component-snapshot.mjs --connection "$REFERENCE_CONNECTION" --application "$REFERENCE_APPLICATION_ID" --workspace "$REFERENCE_WORKSPACE" --schema "$REFERENCE_SCHEMA" --compiler /path/to/sqlcl/lib/apexlang-compiler.jar --output /tmp/apexrest-component-snapshot-new
node scripts/capture-component-snapshot.mjs --snapshot /tmp/apexrest-component-snapshot-new --publish resources/components/source
npm run catalog:verify
npm run catalog:build
npm run catalog:check
npm run build
```

`catalog:verify` запускає SQLcl без підключення до БД і перевіряє кожен підтриманий рецепт у його точному scaffold. Команда записує hashes файлів та вивід компілятора; SQL prerequisites не виконує. Перед пакуванням перевірте diff кількості джерел, unresolved-рецепти й розбіжності версій. Для швидшої локальної ітерації `node scripts/verify-component-recipes.mjs --changed` повторно перевіряє змінені входи; builder однаково вимагає чинні докази для кожного `ready`-рецепта.

Перевірений пакет містить фактичні метадані, власні пояснення, приклади й атрибуцію джерел. До нього не входять сирі експорти, облікові дані розгортання, приватні URL та compiler bundle. Перед заміною комплектної ревізії новий знімок проходить перевірку інвентарю та diff вмісту. Зберігайте чинні IDs, якщо їхнє значення не змінилося.

Межі перевірки й розповсюдження наведено у [стані реалізації](implementation-status.uk.md), [матриці приймання](acceptance.json) та [наступних діях](next-actions.uk.md). `apexrest@1.1.0` опубліковано як npm `latest`; [запис публікації](evidence/npm-110-publication.json) підтверджує цілісність пакета в реєстрі та чисті локальне й глобальне встановлення. Публікація не підтверджує поведінку в браузері.

# SQL через ORDS

[English](ords.md) | Українська

Виберіть **Settings → Database network transport → ORDS HTTP(S)**, коли listener Oracle, зазвичай на порту 1521, недоступний, але доступна ORDS-адреса схеми. Це спільне налаштування плагіна для нових операцій. Поточні операції зберігають обраний транспорт. Після зворотного перемикання доступні прямі з’єднання Oracle.

## Налаштування підключення

Відкрийте локальну панель розробки й збережіть посилання APEXREST на підключення, вказавши URL схеми, **Database username** і **Database password**. Використовуйте облікові дані наявного користувача Oracle Database, якому дозволено доступ до схеми через ORDS; окремий обліковий запис ORDS не потрібен. Збереження посилання налаштовує плагін для роботи з цим обліковим записом. Використовуйте окремі посилання для `readConnectionRef` і `deployConnectionRef`, якщо вони мають різні права. URL визначає REST-enabled схему, наприклад `https://ords.example.invalid/ords/app_user/`; її псевдонім може відрізнятися від імені користувача бази даних. Використовуйте URL схеми від адміністратора, а не адресу застосунку APEX чи URL із `/_/sql`. URL має використовувати `https:`; звичайний `http:` приймається лише для `localhost`, `127.0.0.1` або `[::1]`, бо інакше пароль бази даних передавався б відкрито.

Еквівалентне інтерактивне підключення Oracle:

```sql
connect -orest app_user@https://ords.example.invalid/ords/app_user/
```

APEXREST зберігає транспорт у `$APEXREST_HOME/sqlcl.json`, параметри підключення — у `$APEXREST_HOME/connections.json`, а паролі окремо — у `$APEXREST_HOME/credentials/`. Це локальні файли рівня плагіна, зазвичай у `~/.apexrest`, а не файли проєкту. У POSIX файли секретів доступні лише власнику; це не зашифроване сховище паролів. Не додавайте їх до системи контролю версій і не поширюйте. Збережені з’єднання SQLcl використовуються лише для прямого транспорту; ORDS не потребує збереження з’єднання в SQLcl.

Під час редагування збереженого посилання поле **Database password** у локальній панелі залишається порожнім. Якщо його не заповнювати, збережеться наявний пароль для тієї самої адреси й користувача бази даних. Зміна адреси або користувача потребує облікових даних нової ідентичності. Вбудований MCP-інтерфейс не передає паролі через виклики інструментів: використовуйте локальну панель або параметр CLI `--password-file`. CLI читає локальний файл пароля замість передавання пароля аргументом команди. Цей файл має бути звичайним файлом, а не символьним посиланням, і в POSIX бути доступним лише власнику (`chmod 600`); інакше команда завершується з `PASSWORD_FILE_UNSAFE`.

Після повернення до **Direct Oracle listener** виберіть наявне збережене з’єднання SQLcl зі списку в налаштуваннях. Відкриття налаштувань Direct завантажує локальні назви з’єднань SQLcl без відкриття сесії бази; **Refresh saved connections** читає їх повторно на запит. Панель показує стани завантаження, порожнього списку й помилки, а після невдачі — кнопку **Retry**. Звичайне оновлення панелі не завантажує цей список повторно. Перемикання транспорту зберігає як прив’язку до прямого з’єднання, так і облікові дані ORDS для посилання. Див. [елементи керування панеллю](panel.uk.md).

```sh
apexrest connection add dev-read \
  --ords-url https://ords.example.invalid/ords/app_user/ \
  --ords-username app_user --password-file /path/to/local/ords-password.txt
apexrest sqlcl configure --mode cli --database-transport ords --json
apexrest connection test dev-read --json

# Return to the existing direct connection mappings.
apexrest sqlcl configure --mode cli --database-transport direct --json
```

Адреса та користувач у прикладі не є налаштованою або перевіреною ціллю. Перед розгортанням додайте відповідне посилання `dev-deploy`. За відсутності параметрів ORDS операція завершується явною помилкою; плагін не повторює її через прямий listener. Перевірки бази даних, сервісу, схеми, workspace та застосунку з конфігурації проєкту залишаються чинними.

## Імпорт і експорт APEXlang

Для SQL та запитів метаданих ORDS використовує OREST-драйвер SQLcl. Режим виконання — CLI; поєднання офіційного SQLcl MCP з ORDS відхиляється явно. Власні інструменти Codex MCP плагіна APEXREST залишаються доступними.

Для запитів метаданих адаптер задає значення bind-змінних клієнтським синтаксисом SQLcl `VARIABLE ... = ...`. Це усуває окремий запит `EXEC` для вихідної bind-змінної, який REST-драйвер може відхилити з `ORA-17283`.

Операції APEXlang використовують компілятор і бібліотеки Oracle з вибраної інсталяції SQLcl. Комплектний Java-засіб виконує імпорт APEXlang одним REST-запитом, щоб стан пакетів інсталяції зберігався між скомпільованими блоками. Експорт використовує `APEX_EXPORT` і CLOB із ZIP у base64, обходячи відсутню в REST-драйвері операцію отримання BLOB. ZIP зберігає сформовані Oracle файли APEXlang та метадані `.apex`. SQL-копії експортуються тим самим шляхом. Офлайн-генерація та валідація зберігають наявні команди Oracle SQLcl.

ORDS REST SQL фіксує успішні запити й відкочує невдалі. Окремі запити не мають спільного стану сесії бази даних; помилка пізнішого запиту не відкочує попередній успішний. Наявні перевірки дозволу на розгортання, ідентичності, резервної копії, змін цілі та невідомого результату зберігаються. Тайм-аут або переривання після початку імпорту потребує звіряння перед повторною спробою.

## Передумови й перевірка

Для APEXlang потрібні SQLcl та APEX версії 26.1 або новішої й відповідні права на workspace/схему. ORDS має надавати REST-Enabled SQL для вибраної схеми та приймати вказані облікові дані бази. Для кожної адреси, крім loopback, HTTPS обов’язковий.

Java-засобу потрібен JDK 21 або новіший із модулем `jdk.compiler`; сам керований JRE для SQLcl його не містить. Адаптер спочатку перевіряє налаштовану Java, потім — уже встановлений JDK із `JAVA_HOME` або `PATH`. Цей вибір стосується лише засобу й не змінює налаштувань керованого JRE для SQLcl. Якщо відповідного JDK немає, `ORDS_JDK_REQUIRED` зупиняє операцію до передавання облікових даних або запитів до бази. Адаптер не завантажує Java й не змінює конфігурацію runtime автоматично.

[Перевірка CLI з підключенням](evidence/ords-connected.json) фіксує дозволений цикл імпорту/експорту без змін на приватній тестовій цілі. Повторні експорти до імпорту були детермінованими, `deploy.apply` створив справжню SQL-копію, а експорт APEXlang після імпорту побайтово збігся для всіх 21 файлу: 14 файлів APEXlang, двох JSON і п’яти PNG. Це підтверджує перевірений склад застосунку та сценарій без змін. Імпорт зі змінами, додаткові варіанти компонентів, SQL-відновлення, переривання/звіряння, віддалений rollback і Windows залишаються окремими перевірками. Користувач явно відклав браузерну перевірку застосунку. Повні межі доказів наведені в [стані реалізації](implementation-status.uk.md) та [наступних кроках](next-actions.uk.md).
